# Decoded source cache

The app must offer a settings panel for decoded-source caching. The cache defaults to enabled with a 10 GB decimal disk budget. Merrill and Quattro default on, Classic off. Each family has its own checkbox. These are workspace preferences, separate from photo editing sidecars.

Storage must stay under the platform temporary directory. Cache identity includes canonical source location, modification time and file length, plus the decoded-format version. A moved or modified original must not reuse another source's decoded samples. The cache must retain the original sensor layout, sample values, camera matrix encodings and property-list order. Photo edits do not invalidate decoded data.

Successful reuse updates LRU recency. Eviction removes least recently used entries until the configured budget is met. Cache writes and maintenance run in bounded background work and must not delay image delivery. Failed or incomplete cache entries fall back to original decoding. Cache failures must not prevent ordinary rendering. Platform reboot boundaries invalidate retained entries. The app must not offer an arbitrary cache location outside temporary storage.

The settings panel must offer the master switch, disk budget, architecture checkboxes, cache usage, a background decoding thread budget and a clear-cache action. The thread budget must range from one to the platform’s available logical core count and persist as an application preference. It defaults to three, capped at that core count. More threads may decode several photos ahead concurrently. Active photo loading and its decoder children must use User Initiated QoS on macOS. Background decode workers must use Background QoS. Turning caching off retains existing disposable files until eviction, clearing or reboot, but prevents their use and further insertion. [Display previews](./browser-previews.md) share this temporary directory, source identity, architecture policy, LRU eviction, and byte budget. Clearing removes both kinds of entry. Usage includes preview bytes while the photograph count describes decoded sources. No multi-photo decoded RAM cache is introduced.

The app must predecode eligible files beneath the currently opened root using a bounded group of background photo workers and a bounded pending foreground write. Each speculative photo uses one decode thread, keeping nested sensor-plane work within the configured CPU budget. Active photo decoding may still parallelize its independent planes. Dispatch photos in the browser's displayed folder/image order from top to bottom. Concurrent jobs may finish in a different order. Selecting another photograph must not reorder the remaining background queue. Respect all architecture switches for prefetch as well as foreground reuse. Queued and active photo rendering and scopes take priority. Background reading, decoding and insertion must yield at bounded checkpoints, with lower CPU and I/O priority on macOS. A new foreground request must cancel in-flight speculative prefetch at those checkpoints instead of retaining partial decoder buffers while paused. Decoder child threads must inherit cancellation. Interruptions must retry unfinished files at the front of the remaining queue in browser order after foreground work finishes. A changed source folder or cache policy discards the old attempt. Full embedded-preview reads must also use bounded chunks. Foreground source loading must use an independent thread and must not wait for prefetch completion. Submitted import batches retain their separate pause/resume policy. In-flight decoded data must remain bounded by the configured worker count and the pending foreground insertion. Cache publication and eviction must remain serialized across concurrent jobs.

Grid and list previews must show small muted status dots beside filenames. In the grid, place the dot at the bottom right in the caption area, outside the photograph. Gray means disabled or unsupported caching, yellow means queued or being prepared, green means ready, and red means supported but currently uncached. Red may follow eviction, clearing, a failed insertion or an entry larger than the budget. Hover text must explain the state. Unknown eligibility may remain yellow while metadata checking is queued. The badge must follow source identity, policy, clearing and eviction. Readiness scanning runs off the UI thread. A corrupt entry still falls back to original decoding when opened. Clearing the cache stops the current prefetch pass. A folder larger than the budget must not cause an endless decode/evict loop. Revisiting the directory or changing policy may start another pass.
