# Decoded source cache

The app must offer a settings panel for decoded-source caching. The cache defaults to enabled with a 10 GB decimal disk budget. Merrill and Quattro default on, Classic off. Each family has its own checkbox. These are workspace preferences, separate from photo editing sidecars.

Storage must stay under the platform temporary directory. Cache identity includes canonical source location, modification time and file length, plus the decoded-format version. Source changes must invalidate the associated identity during background refresh or folder reload. Foreground access to a ready entry uses the last background-verified identity without opening or statting the source. Cached entries may remain usable while the original is unavailable. A different observed identity must never reuse another source's samples. The cache must retain the original sensor layout, sample values, camera matrix encodings and property-list order. Complete entries must also retain exact original X3F bytes, capture properties, saved editing settings, a prepared thumbnail and any suitable larger preview. Original bytes and metadata companions share the same identity and disk budget as decoded samples. Photo edits do not invalidate decoded data.

Successful reuse updates LRU recency. Eviction must prefer keeping the current selection neighborhood. Remove unrelated entries in LRU order, then farther neighbors before closer ones when necessary. Within one photo, decoded RAW data takes preference over its display preview. Consider an incoming entry before deleting existing files. A farther insertion must be skipped if admitting it would evict closer data. The configured byte budget still applies when the full neighborhood cannot fit. Cache writes and maintenance run in bounded background work and must not delay image delivery. Failed or incomplete cache entries fall back to original decoding. Cache failures must not prevent ordinary rendering. Platform reboot boundaries invalidate retained entries. The app must not offer an arbitrary cache location outside temporary storage.

The settings panel must offer the master switch, disk budget, architecture checkboxes, cache usage, a background decoding thread budget, separate behind/ahead prefetch counts and a clear-cache action. The neighbor counts must persist as application preferences and default to three photos behind and seven ahead, plus the current photo. Either count may be zero. The thread budget must range from one to the platform’s available logical core count and persist as an application preference. It defaults to three, capped at that core count. Workers must share a FIFO queue of independent sensor layers, ordered by photo priority and then R/G/B. A free worker takes the next queued layer immediately. With five workers, R/G/B of the first photo and R/G of the second may run together, followed by its blue layer as soon as any slot frees. Photo completion must not impose a group barrier. Interleaved Classic streams use one task in that pool. Active photo loading and its decoder children must use User Initiated QoS on macOS. Speculative RAW decode workers and their photo coordinators must use Utility QoS on macOS, below active User Initiated work. Cache maintenance and unrelated background jobs retain Background QoS. Turning caching off retains existing disposable files until eviction, clearing or reboot, but prevents their use and further insertion. [Display previews](./browser-previews.md) share this temporary directory, source identity, architecture policy, LRU eviction, and byte budget. Clearing removes both kinds of entry. Usage includes preview bytes while the photograph count describes decoded sources. No multi-photo decoded RAM cache is introduced.

The app must predecode eligible files only within the configured neighborhood of the selected photo, using a bounded shared layer pool, a bounded number of photo I/O coordinators, and a bounded pending foreground write. Counts follow the browser’s visible folder/image order, excluding concealed rows except for a concealed photo still active in the viewport. Clamp at either end without extending the opposite side. No selected photo means no speculative decode. Start with the current photo, then increasing distance, favoring forward neighbors on ties. Changing selection, filtering, folder or policy must replace the remaining queue and cancel obsolete speculative work. A repeated unchanged snapshot must not restart a completed or cleared pass. Independent sensor planes must use the shared pool and stay within its configured worker count. Borrow compressed inputs for the scoped layer work without copying full compressed planes. Source reading and cache publication remain separate from those CPU workers. Active photo decoding may still parallelize its independent planes. Concurrent jobs may finish in a different order. Respect all architecture switches for prefetch as well as foreground reuse. Queued and active photo rendering and scopes take priority. Background reading, decoding and insertion must yield at bounded checkpoints, with lower CPU and I/O priority on macOS. A new foreground request must cancel in-flight speculative prefetch at those checkpoints instead of retaining partial decoder buffers while paused. Decoder child threads must inherit cancellation. Interruptions must retry unfinished files at the front of the current neighborhood queue after foreground work finishes. Superseded queues must not return. A changed source folder or cache policy discards the old attempt. Full embedded-preview reads must also use bounded chunks. Foreground source loading must use an independent thread and must not wait for prefetch completion. Submitted import batches retain their separate pause/resume policy. In-flight photo buffers must remain bounded by the configured worker count and the pending foreground insertion. Cache publication and eviction must remain serialized across concurrent jobs.

Grid and list previews must show small muted status dots beside filenames. In the grid, place the dot at the bottom right in the caption area, outside the photograph. Gray means disabled or unsupported caching, yellow means queued or being prepared, green means the complete local bundle is ready, and red means supported but currently uncached. Red may follow eviction, clearing, a failed insertion or an entry larger than the budget. Hover text must explain the state. Unknown eligibility may remain yellow while metadata checking is queued. The badge must follow source identity, policy, clearing and eviction. Each photo must publish readiness as soon as its complete local bundle is written, without waiting for other photos or a complete folder scan. All image assets must be extracted from the same original buffer used for decoding. Foreground selection, rendering, previews and copying an original for import must use a ready bundle without synchronous source-card reads. Capture/default loaders and preview recipe checks must use its local metadata snapshot. Source identity and external sidecar changes are checked in background work. Successful local sidecar saves update cached settings asynchronously. Readiness scanning runs off the UI thread. A corrupt entry still falls back to original decoding when opened. Clearing the cache stops the current prefetch pass. A neighborhood larger than the budget must not cause an endless decode/evict loop. Selecting a different photo, changing visibility or changing policy may start a new neighborhood pass.

Implementation and validation are recorded in the [prefetch window plan](../../plans/archived/cache-prefetch-window.md).

[Browser thumbnail demand](./browser-previews.md) must take priority over speculative source reads, publication and maintenance while yielding to selected-photo work. In-memory sensor-layer tasks may finish under thumbnail demand at Utility QoS. Their existing foreground cancellation remains authoritative. Submitted batches outrank speculative work. Passive import-history scans remain background work.

Readiness scans and eviction bookkeeping must follow the same cancellation policy as speculative decoding. A changed selection must stop an obsolete directory walk at its next checkpoint, and the replacement decode neighborhood must take priority over a directory-wide readiness scan. Interrupted scans must not publish stale readiness or postpone a retry as though the scan completed.

The [single-read cache plan](../../plans/archived/single-read-cache.md) records complete-bundle readiness, source-independent selection and import, and loading diagnostics.
