# Performance diagnostics

## Purpose

The application must support empirical attribution of runtime across UI interaction, scheduling, source access, caching, processing and presentation. Diagnostics must support both exploratory profiling and repeatable correctness and performance-regression checks. Renderer experiments must use validated capture and correctness checks.

## Measurement contract

Measurements must distinguish elapsed latency, CPU execution scopes, queue residence, explicit waits, GPU execution, resource retention and delivery. Host elapsed time must not be described as CPU-active time or inferred GPU execution. Parallel and nested intervals must remain distinguishable rather than being added into misleading totals. CPU work must use a common monotonic timeline. GPU timestamps must retain their clock provenance and associate with submissions without inventing a calibrated host position.

An interaction must be traceable through its desired render targets, coalescing or replacement, execution, cache decisions, completion admission and the frame that uses its delivered image. Reuse existing task, photo, purpose, revision and artifact identities. Background prefetch, scopes, navigator and exports must remain distinguishable from foreground work. Cancelled, superseded and failed work must have explicit outcomes.

The diagnostic model must support future concurrent reduced-grid execution across photographs and graph nodes without assuming one photograph finishes before another begins. Preserve per-photo node dependencies and distinguish CPU preparation overlap, interleaved submissions and actual GPU execution overlap. Report first-current-result latency, complete-group latency, throughput, fairness, obsolete work and peak in-flight resources. Diagnostics must observe scheduling independently of its implementation and must not introduce execution barriers.

Cache diagnostics must distinguish local decoded data, corrected/reduced processing inputs, graph checkpoints, displayed images and browser previews. They must report hits, misses, invalidations, admission and eviction with reasons and resource sizes. Actual source payload reads must identify original versus local storage independently of readiness indicators. Recording a cache observation must not change recency or load a payload merely to inspect it.

Cache-budget workflow tests must report foreground delivery separately from background Whole preparation. Record logical retained resources at worker boundaries with available task identity; identify per-image references as potentially shared and non-additive. Keep retained-resource snapshots distinct from process footprint, transient allocation traffic and physical GPU residency. These measurements belong in test evidence and traces; no memory-usage UI is required.

Workflow coverage must include native/native, reduced/reduced, mixed-resolution editing and native-detail switching through zoom or loupe. Use these cases to check shared-budget retention and reuse independently of selection count, and to detect when background Whole preparation displaces useful regional processing state.

Native captures should connect exact graph-output demand and availability with numerical-cache instance/version identities and scalar retained-checkpoint snapshots at shared execution boundaries. A capture started with warm data must describe the participating cache without relying on earlier admission events. Offline explanations should join these facts with existing task timing and budget observations. Missing or truncated history must remain unknown. Referenced checkpoint bytes must not imply freed memory, and observed rebuilding must not be presented as measured savings under a different policy. Diagnostics must preserve buffer lifetimes and avoid enabling headless per-node memory scans merely to explain a native task.

## Instrumentation and capture

Instrumentation must have one shared ownership model and reusable scoped APIs. Common execution boundaries should supply coverage automatically. Routine profiling must not require scattered formatted log statements or per-pixel/per-element events. Existing stage measurements and GPU activity counters should migrate into the shared model instead of establishing a parallel profiling system. The viewer and machine reports should preserve scoped application call hierarchy and actual thread ownership. Uninstrumented function internals may require a separate sampling profiler.

Captures must be bounded and locally inspectable, with machine-readable query results. Record capture configuration, build and input identities, processing settings, processing quality, effective working scale, hardware and intended cache state. Overflow and missing observations must be explicit. Ring-buffer recordings must periodically refresh incremental metadata so retained recent events remain decodable after older packets are overwritten. Disabled instrumentation must avoid formatting and recording work. Enabled capture must not block the UI or rendering on output, or add GPU waits merely to obtain timestamps. Measure capture overhead separately.

Scripted scenarios must run the real application and produce the same capture format as manual use, with scenario steps, expected outcomes and performance results attached. Existing native smoke and pointer scripting should be reused where they exercise the intended path. Distinguish direct application-method actions from physical/input-dispatch coverage. A user must also be able to record ordinary app use and save a locally readable capture and summary on demand without closing the application. The viewer should provide an interactive timeline with thread/task lanes, nested timings, counters and interval inspection comparable to a browser performance view.

Behavioral checks must cover applicable editing controls and user journeys across the supported camera families and available RAW sizes. For every applicable slider, exercise a sustained multi-photo drag with differing starting values while rendering progresses. Check the shared numeric display policy, stable panel and control geometry, continued pointer response, relative per-photo edits and eventual delivery of the final requested state. Record unavailable and untested controls explicitly. Use actual widget input for this coverage and keep direct-command checks separately identified. Capture enough structured state and failure artifacts to identify the control, input sequence, photo settings, displayed values and geometry. Preserve replayable actions and seeds when generated sequences are used.

The default live capture buffer is 128 MB. Manual saves should retain the latest four completed, explicitly retention-managed capture bundles per destination parent, including their derived reports. Cleanup must happen off the UI thread after a successful save, preserve the newly saved capture and exclude scripted evidence, unrelated data and incomplete folders.

Every explicitly started capture must save on orderly application exit, including one still starting. A configured capture directory is used when supplied. Otherwise the recording is saved under the platform temporary directory in `foveonic-captures/`. Closing during an already-requested save must finish that save rather than create a second capture. Shutdown may wait for recorder completion after interaction has ended. Ordinary unrecorded launches must not create capture output. Forced termination is outside this orderly-exit guarantee.

## Reproducible test inputs

Maintained tests must be easily rebuildable from the repository and declared photographic inputs. The owner's photographs come from the example release. Other camera-family originals use a tracked manifest of publisher download URLs, content hashes and source-reported license/credit metadata, without rehosting them in that release. Keep drivers, fixture manifests, recipes, expected behavior and rebuild commands in version control. Resolve inputs without personal absolute paths. Generated aliases of originals, sidecars, caches, renders and traces belong in disposable output directories. Required test behavior must not depend on ignored helper scripts or manually edited local recipes.

Frozen numerical expectations must identify the approved code revision, source contents, recipes and generation procedure. Rebuilding a baseline must reproduce that approved result rather than bless the candidate implementation's output. Local cleanup must preserve unique inputs and approved expectations until their reproducible replacements are verified. Optional research requiring other inputs must report those dependencies explicitly and cannot stand in for a reproducible acceptance gate.

## Validation

Correctness checks must validate causality, accepted output identity, complete task settlement, processing quality, effective working scale and expected work/reuse independently of timing thresholds. Performance scenarios must separately cover initial loading, warm disk with cold processing state, retained processing, editing, switching, memory pressure, rapid supersession and multi-photo delivery. Keep mixed-resolution Quality/Speed coverage at both the 2 GiB default and an explicit 1 GiB low-memory budget. Record the latency effect of lower budgets without treating slower but correct delivery as a behavioral failure.

Unchanged cached selection and same-photo reopening must perform zero original RAW payload reads, decoded-cache payload reads and photographic GPU dispatches for retained photographs. Check these work counts independently of accepted result identity so discarded work cannot hide a regression. Existing task purposes distinguish photographic rendering from auxiliary scopes, navigator and presentation work. Unrelated background prefetch reads must remain visible separately.

Shared behavioral scenarios must remain usable when independent photographs finish in different orders. Compare each delivered photo and revision with its expected numerical result and validate dependencies, cache ownership, cancellation, freshness, final settlement and resource policy. Keep implementation-specific scheduling-policy tests distinct. Capture the current serial execution baseline before experimenting with concurrent or stage-grouped execution.

Maintain an acceptance inventory of the application's supported user paths and their expected outcomes. Run related subsets during development and an explicit broad suite before release. Reports must distinguish executed checks, uncovered behavior, missing fixtures and failures. Cover transitions between editing, selection, processing quality, viewport tools, inspection, persistence, processing and error recovery rather than relying only on isolated feature tests. Bounded generated sequences must retain their seed and complete replay actions. Test copied-original bytes, frozen export settings and encoded image readability separately from floating render equality. Keep natural latency comparisons separate from controlled completion-order tests and screenshot capture.

Expected user-visible behavior must be derived independently of the application state being checked. Permit compatible intermediate previews and any valid completion order, then verify the latest desired state after foreground work settles. Keep unit, headless numerical and headed behavioral evidence distinct. Correctness checks must not depend on latency thresholds; matched unrecorded runs provide separate latency baselines, and traced runs provide attribution and failure evidence.

Headless and real-app checks should report common observations and assertion outcomes in one test-result shape where their evidence describes the same behavior. Reuse those assertions without making an engine-only run claim user-interface coverage. Each driver retains its own detailed evidence and identifies how it exercised the application.

Opt-in app image verification must read the settled rendered artifacts retained by the application. Check the intended edit independently before replaying its exact effective settings in fresh headless processing. Preserve transient render settings in diagnostic snapshots without changing photo-sidecar serialization. Compare complete floating samples and their storage and view geometry through the same assertion used by headless baselines. Perform image readback and image file writes off the UI thread, after measured interaction and capture saving; run fresh verification after the app exits. Report numerical equality separately from physical screen presentation and latency.

Behavioral coordination checks must derive expected edits from declared recipes and explicit user actions. Check all participating photographs, including unchanged targets, without depending on completion order. A controlled image-delivery pause may make an in-flight handoff deterministic, but it must be identified as harness work and released on failure. Reuse assertions must check actual payload reads and photographic dispatches for the affected targets. Rebuild assertions must include runtime evidence that the required photo was retained and then evicted.

Latency comparisons must identify window and viewport dimensions and pixel density. Missing geometry cannot establish a comparable workload. UI update cadence may be reported with a caller-selected gap budget, separately from physical input and presentation latency. Foreground/background tests must observe real background work, and foreground settlement must remain distinct from waiting for that work to finish.

Native presentation diagnostics should distinguish host time spent acquiring a surface image, submitting window commands and presenting. Preserve exact host endpoints and viewport/pass identity without adding GPU completion waits. Pointer-motion observations describe input reaching the app. Sustained motion tests must derive their path from elapsed monotonic time so slow frames cannot silently slow the simulated movement. Keep retained-coverage controls separate from motion that requests replacement detail, with screenshots and verification readback outside measured intervals.

Performance comparisons must use matched builds, settings, inputs, hardware and cache conditions, with repeated samples and reported variability. Timing budgets belong to controlled performance runs rather than ordinary portable unit tests. Detailed attribution runs must remain separate from baseline latency measurements. Profiling launchers must check for other application, compiler and measurement processes before starting. They should record concurrent workloads during each run and mark contaminated timings separately from behavioral correctness. Native frame submission is not proof of physical screen presentation. Sampling profilers and platform tools may complement application instrumentation for unmarked internals and system scheduling.

## Interrupted speculative reads

Physical source/cache reads must remain counted when speculative preparation is interrupted, including reads for currently displayed photographs. An incomplete decoded-cache read may be classified as cancelled only when its own decoded lookup reports `background prefetch interrupted`, its enclosing prefetch operation reports interruption, its source matches both reports, and the read explicitly records zero I/O errors. Missing scope/cause evidence and checksum or I/O errors remain failures. Cancellation must not waive no-read or retained-reuse assertions. Report cancelled byte counts separately from failures.

## Automatic-resolution setup

Initial selection in a primed scenario must use the decoded disk cache without original-file payload reads. Its observed acquisition counts and latency remain diagnostic: photographic layout may resolve to a finer working grid after initial images arrive, requiring sealed upstream inputs again. A prefetched reduced working set does not promise the eventual display grid. Disk-disabled setup likewise has no fixed original-read count. Failed and incomplete reads remain failures. Settled warm edits and cached-reuse actions retain their declared zero-read and no-unnecessary-work assertions. Initial acquisition minimality must not be reported as verified by those warm-edit checks.
