# Interactive rendering

The [implementation architecture map](../interactive-rendering-architecture.md) describes current ownership, request flow and distributed policy. The requirements here remain the behavior contract.

## Requirements

- Slider-to-image feedback **must** be the priority; some delay switching photos is acceptable. Measure completed input-to-image latency and UI frame stalls separately from submission and scope latency.
- Initial source-load profiling **must** separate complete raw-file reading into memory from in-memory decoding, and report total source-open wall time. Filesystem cache state **must** be identified as uncontrolled unless explicitly measured; warm local-drive reads do not establish slow SD-card latency. Warm editing reuses the decoded source and **must not** be charged its historical load timings.
- Full interactive processing **must** preserve full-quality samples and the final/export recipe. Explicit preview choices use the shared [power-of-two working-grid contract](./small-previews.md). Automatic reduced-quality dragging previews are not selected.
- A working photo **may** retain immutable GPU checkpoints. Keys **must** include effective output-relevant parameters, upstream output versions, source and engine identity. Retained data **must not** enter execution scratch. Retained checkpoints **must** be trimmed back to the shared memory target in the [scheduling order](./render-scheduling.md#working-set), and explicit clear **must** release their owners. Accounting **must** count shared allocations once.
- A Merrill working photo **may** retain one successful camera-repair preparation for its immutable source and effective repair threshold. Its logical CPU retention **must** be limited to 4 MiB, reported separately from retained GPU buffers, and cleared on engine change or when the working photo is dropped. Oversized preparations **must** run without retention. Allocator overhead and graph-version keys are separate from this logical limit.
- Retain the active edit's unchanged input boundary for native whole Full and the current preview grid, rather than every earlier layer. Both working sets **must** share one memory target and may share matching immutable upstream buffers. Changing between regional and whole-frame rendering **must not** displace valid active-edit inputs solely because output names are shared. Initial or changed grids may also retain the photographic-response input so the first exposure edit can reuse it. Detail amount remains a priority. A control **may** affect several operations; processing-owned effective parameter keys and graph dependencies **must** identify affected work and invalidate its input cache correctly. Version metadata **may** remain for every output without retaining its buffers.
- Single-photo editing **should** target around 2 GB steady and 4 GB peak application memory on a 16 GB machine. Multi-photo Speed cache sizing follows the [per-image heuristic](./render-orchestration.md#reuse-and-resource-ownership). Retained memory caching must have a user-set target with a sane default, separate from the disk cache. Count shared allocations once. Essential live data and temporary processing may exceed the retained-cache target and must remain visible in profiling. See [multi-edit](./multi-edit.md).
- Processing **must** remain off the UI thread. The coordinator must own desired render work and completion admission per photograph and purpose. It submits, replaces and cancels jobs in the [Scheduler](./render-scheduling.md) queue. Superseded expensive work **must** stop at safe preparation/graph-stage boundaries. Already submitted GPU work is not forcibly cancelled.
- A completed image **must** be deliverable without waiting for scopes. Scope work **must** yield to a pending image request and scope replies **must** identify the photograph and exact displayed artifact they analyzed.
- While dragging, completed older frames for the same photo and inspection root **may** provide progressive feedback, without overwriting current editing settings or being mislabeled as current. Other-photo/root and out-of-order replies **must** remain rejected. The newest request **must** eventually display after interaction stops.
- Export **must** remain non-cancellable, use current requested settings, and preserve immutable displayed results and provenance.
- Asynchronous [import batches](./import-workflow.md) must freeze settings at submission and leave interactive controls available. They run as Export jobs in the [Scheduler](./render-scheduling.md) queue and must yield I/O and GPU work to higher tiers. The current submission may finish before foreground work proceeds. Background execution must not build an entire frame of queued GPU work ahead of interaction.
- Navigator presentation **must** use a small GPU-generated display-ready texture and ordinary egui image drawing, preserving overlays, interactions and the main viewport clipping fix. Regenerate only for content/mapping changes; no photographic readback or scope dependency. Main-image latency takes priority: navigator updates **may** lag during sliding, with explicit revision/mapping/source pairing and no other-photo/root mismatch.
- Render work **must** follow the [Scheduler priority tiers](./render-scheduling.md#priority). Users **must** be able to disable background full-image completion for battery use. Useful regional delivery and foreground settlement must remain independent of that continuation.

## Coordination

The editor owns authored settings and selection. The render coordinator owns requested work, per-target generations and completion state. The [Scheduler](./render-scheduling.md) owns execution and the working set. Immutable completions must not overwrite authored settings. A multi-edit updates its desired target set atomically and must preserve work for other selected photographs when one changes.

Cancellation is advisory. Admission must reject incompatible or out-of-order completions even when a cancelled job finishes. Cache admission and current-view admission are separate decisions. Crop/rotation and memory-configuration changes must preserve matching pixel work. Before and inspection are distinct purposes, while scopes and picks identify their input image. Active feedback receives priority while other selected targets make progress during continuous editing. After input stops, every selected target must settle on its latest requested state.

Completion classification must explicitly distinguish reusable pixels, per-photo result feedback and delivery to the active view or an overview tile. The UI applies those decisions without repeating their compatibility conditions. The existing coordinator owns exact settlement, source identity and admitted revision ordering. Improvements to this path should preserve the current scheduling and cache owners and be validated in small usable checkpoints before a broader orchestration migration.

Use existing Rust worker/channel primitives. Test the observed completion-order, target-removal, Before-cancellation and continuous-input cases with a deterministic fake executor, then validate real GPU delivery. This does not require a generic actor framework, additional runtime or speculative recovery system.

## Startup

The application must present a loading window before preparing the photographic engine. Engine pipeline preparation, calibration loading and processing-worker initialization must run off the UI thread. Native window/display configuration stays on the UI thread. The loading window must remain responsive and show actual completed graphics-program counts when available, followed by finishing setup. Counts indicate completed pipeline creation calls, not a time estimate or driver-internal compilation percentage.

Completed application preparation must cross to the UI through heap-owned storage. Receiving the result must not materialize the complete application state on Windows' default main-thread stack.

The initial loading window should be compact and centered horizontally and vertically on the screen where native placement is available, with a large Foveonic icon on the left and application name, status and progress on the right. Its light or dark artwork must match the effective system appearance. When preparation completes, restore the workspace's remembered size and maximized/fullscreen state and its remembered native position. Without a remembered position, the workspace should expand around the loading window's center. On Windows, the restored workspace must stay inside the area its monitor's taskbar leaves free, at the display's scaling, and shrink when it is larger than that area. The workspace must remain usable if the window manager ignores a resize request.

Closing during preparation must not join the preparation worker or replace saved preferences or workspace geometry with loading-window defaults. Preparation failures must show a readable error and allow closing the window. The native framework still prepares its graphics device and basic UI renderer before application drawing becomes possible.

## Photograph-loading progress

The photograph-loading area must show a progress bar and total milliseconds instead of a spinner and loading text. Normal processing uses five equally sized sections: file reading, decoding and metadata, recipe preparation, graph execution, and display preparation/delivery. The graph section advances in equal increments at completed required graph operations. Interactive GPU stages report after their existing completion waits. No time-based interpolation or new per-stage GPU waits are permitted.

The timer starts when the request enters the worker queue and freezes when its display-ready image reaches the UI. It includes queueing, source I/O, decoding, metadata, preparation, rendering and display texture completion. Deferred scopes and navigator work are excluded. Physical screen scanout is not measured. Cached loading and cached graph work complete their applicable sections immediately. Superseded requests must not advance or finish a newer request's progress. Progress reporting must remain separate from the bounded image-reply channel. Errors must remain visible.

DNG export reports its combined preparation/render completion on return from export. Its internal appearance fitting is not split into graph-stage updates. Export remains non-cancellable. Documentation screenshot captures must omit elapsed timings.

## Implementation direction

Working photos own immutable source dependencies and retained graph inputs. Reduced working photos may release the file's decoded data after preparing the graph's declared sensor data. Keep separate version/frontier metadata for native and reduced grids, with shared generation identities, immutable buffers and aggregate admission accounting. CLI and export use the same Scheduler and execution path. Keep stage keys beside processing preparation, combine them with upstream output versions in the graph, and retain unchanged inputs feeding affected operations throughout the required continuation, including branch inputs to downstream consumers. Initial reconstruction and photographic-response inputs share the same memory target. Later cache replacement may need a warm-up render. Navigator work is deferred and lower priority than main-image processing. Compare cold/cached float outputs and TIFFs exactly. Include zero gain, disabled stages, setting invalidation, source/engine changes and retained-image checks.

Collect optional UI timing diagnostics and repeatable worker slider sequences. Native interaction evidence is separate from unit/worker conformance. Track findings in the [responsiveness plan](../../plans/ui-responsiveness.md). The first slice has six-original exact output evidence, progressive worker checks, native Detail timing and total-memory samples. Detail remains about 125–143 ms in the measured native workspace, with around 2.1 GiB settled total footprint; worker drag coverage now includes noise presets and all advanced overrides, and synthetic navigator drawing is measured separately. Native pointer-driven acceptance and remaining shared-queue stalls are not complete. New GUI diagnostics are deferred to a later pipeline-visualization view; editing performance and the baseline workspace take priority.
