# Multi-photo editing

## Selection and tools

Browser selection determines which photographs appear in the viewport. It has no editing-count limit and remains the scope for processing, review/file operations and pasting settings. Large selections use progressively smaller viewport tiles down to a minimum readable size, followed by an “N more” overflow indicator. Selection alone must not retain a complete editable processing session for every photograph.

Viewport selection determines which photographs receive editor changes. Selecting one photograph edits it individually. Selecting several enables multi-edit directly, without a separate editing mode or activation button. Browser selection initializes viewport selection to its first L photographs in browser order, where L is the configurable multi-edit limit. The default limit is eight. Additional browser-selected photographs remain outside the editing subset. Normal clicks replace viewport selection. Option-click toggles membership and Shift-click selects a range in displayed visual order, respecting the limit and the [layout contract](./viewport-workflows.md#layout-and-interaction). Editing targets must remain explicit. Each viewport tile has one outline: thick blue when editable, otherwise thin white. Do not add a separate most-recent-photo highlight or inset selection outline. Technical focus may still supply metadata and tool context without another visible selection state. Navigator and scopes controls and new preparation are disabled while multiple photographs are editing targets; late scope replies must not revive the disabled display.

The photograph toolbar must include a Pointer tool with shortcut V. Pointer is the default tool and the only tool that changes viewport selection. Crop, Rotate and picking tools must preserve viewport selection when used on the photograph. Selecting another tool therefore holds the current selection without a separate lock mode. Pointer clicks select or activate a photograph on release, using the existing modifier semantics. Pointer drags pan only the hovered photograph without changing the editing group or active photograph. A drag must not also select on release. Pointer uses an arrow cursor until dragging, then a closed hand. The separate Hand tool and its H shortcut are removed. Space temporarily pans without changing the selected tool. Finishing or leaving an editing tool returns to Pointer. Browser and editor widgets always use ordinary pointer interaction independently of the selected viewport tool. Rotation and other photograph tools must not intercept browser thumbnail clicks or replace their pointer cursor.

Pick tools act on the editing selection: the white balance and haze shadow tone pickers and the Color Range and Advanced range picks. One photograph is a selection of one and uses the same path. With a pick tool armed, the pick cursor shows over every displayed photograph in the editing selection. Clicking a point on one of them measures the value there, on that photograph, and applies it to every editing target, including targets hidden behind the overflow indicator, through the same edit path as the panel. Picks start only when every editing target can take edits, as for the panel. Only the clicked photograph needs an image of its current settings. A displayed photograph outside the editing selection shows no pick cursor and ignores the click. So does a photograph whose relevant section is off, and the tool stays armed.

- White balance sets the measured bias on every target. Sampling a monochrome photograph is refused.
- A haze pick sets the picked shadow color on every target. Targets on Auto leave Auto.
- A Color Range drag changes each weighted band relatively, as a panel slider does, so each target moves by the same amount and clamps at its own limits. It never replaces another target's color settings. Which channels the drag changes follows the clicked photograph's monochrome state, and its band changes reach every target, monochrome or not, as the panel's band sliders do.
- An Advanced range pick adds its range to every target only when all targets have the same range list, the rule the panel's Add button uses. Otherwise it reports an error and changes nothing.

Crop and Rotate are worked directly on a photograph, one at a time, so they need no selection made beforehand (owner, 2026-11-25). With either tool armed, every displayed photograph shows the tool, whether or not it is an editing target, and a drag on a photograph edits that photograph alone. Sidebar controls act on the editing selection, as every sidebar control does: choosing a crop ratio sets it on every editing target and shows “Multi” when they differ. A drag on a photograph is locked to that photograph's own ratio as it is set at that moment, whatever the sidebar shows. No photograph is singled out as most recently selected. Keep selection ownership separate from gesture routing, without a second selection model or explicit multi-edit mode.

## Editing behavior

Multi-photo rendering uses the workspace preview policy independently of how many editing targets are selected. Explicit modes retain their chosen level. [Smart](./smart-preview.md) chooses each photograph’s level from its actual displayed pixel demand. Selecting one photograph inside an overview must not restore the single-photo quality or rerender unchanged pixels. The editing limit bounds the concurrently editable set, independently of the potentially much larger browser selection. Individual photograph edits and preview state must survive switching between photographs, including Import review. Keep a bounded actual-use history of completed results so unchanged target switches and re-adds can reuse them. A completed older or baseline preview must not replace a more recent edited appearance.

Render demand must be independent of editing selection. A retained displayed photograph may need a new quality even when it is not an editing target. Use the same bounded demand for request submission, cancellation, progress and both runtime and UI delivery checks. Changing editing selection alone must not retire useful displayed work. Removing a photograph from display removes its non-editing demand while preserving ordinary bounded history.

The current working set contains every [viewport photo](./view-planning.md#vocabulary), each with its settings loaded. Displaying a browser thumbnail alone must not load its settings or decoded source. Render demand includes editing targets and every viewport photo. Keep the existing admission limit and actual-use retention policy. Visibility does not promote recency. An unresolved or failed member must not block ready siblings or be marked successfully requested. A new request snapshot must retain unchanged in-flight siblings. Refreshing other tiles must preserve the active rendition, inspection and detail workflow.

Before/After applies to every viewport editing target. Camera and Defaults renditions use each photo’s own metadata and authored geometry. Visible non-editing photographs remain Current. Preserve authored settings and each photo’s Current whole/detail images for restoration. Moving technical focus within the editing group preserves Before. Removed targets and late replies must not display the wrong rendition or overwrite Current numeric/default feedback.

Numeric sliders show the minimum and maximum values of the viewport-selected photographs as a range. One photograph uses the same slider, so equal values and a single photograph show one handle. Pressing outside the range moves the nearer handle to the pointer at once, on press, and every photograph by the same offset. Pressing inside the range or on a handle grabs it without moving it. A drag applies a relative adjustment to each photograph from the press, without waiting for the pointer to travel. Steps snap the adjustment; continuous values snap to round values within a pixel. Each value independently clamps at its allowed limits, compressing the displayed range as other photographs approach a saturated value. Double-click resets the affected setting for all editing targets. Numeric field entry assigns one explicit value to all targets.

Dropdowns display “Multi” when their selected values differ. Choosing an option assigns it to every editing target. A mixed label is a display state and must not become a saved photographic value. Shared controls must preserve camera capabilities and valid per-photo settings. The implementation must not silently apply an active photograph’s unrelated settings to other targets.

Import keeps edits in memory under its existing write policy. Browse persists each photograph’s requested settings through the existing asynchronous sidecar owner. Paste reaches every photograph in the browser selection. Copy settings, Save preset and Set as default read one photograph's recipe and are available only when one photograph is edited.

## Interactive latency

Application latency is the current performance priority. Unchanged viewport selection and retained re-adds must reuse compatible results without photographic processing or source payload reads. Repeated edits should reuse every still-valid graph dependency. Avoid unnecessary preparation, submission and delivery work before optimizing arithmetic inside individual nodes.

The immediate workflow is culling a selected set of up to eight similar photographs in Thumb and adjusting exposure quickly. Measure source reads, RAW decoding, decoded-cache loading, upload and processing preparation separately. Prioritize getting the selected set ready and reusing its data. A future loupe will request native detail, but its implementation is outside the current latency work. Reduced previews must preserve the existing ability to recover authoritative native input on demand.

Prepare reusable processing data ahead of demand where the known recipe, priority and shared memory budget allow it. Speculative preparation must yield to foreground interaction and retain its distinct admission and recency policy. Use the existing dependency identities and working-set owners. The complete selected pipeline must follow the [small-preview scale contract](./small-previews.md). Measure necessary native work separately from working-grid work and fixed scheduling cost, and avoid repeating native work when retained dependencies remain valid.

The decoded prefetch neighborhood may also prepare reusable Thumb processing state while the app is idle. Use low-priority host work and the existing foreground gate. New foreground work must interrupt the attempt at processing boundaries. Already-submitted GPU work may finish. Speculative work must not cause eviction or count as use, under the [Scheduler](./render-scheduling.md#working-set) rules. Keep prepared state within the shared memory budget and recover native detail through the existing source path. A decoded-cache readiness indicator continues to describe local source availability, independently of GPU preparation.

The [latency plan](../../plans/multi-edit-latency.md) tracks the application-wide investigation and proposed implementation sequence.

## Resource direction

Disk caching and in-memory caching are separate user concepts and settings. The memory budget must be user-set with a sensible default designed for a 16 GB machine. The default retained-cache target is 2 GiB. Preserve explicitly saved budgets, including 1 GiB for low-memory hardware. Settings must show cache capacity as a whole-number MB count, with every digit visible and no scientific notation or significant-digit limit. Use the existing binary byte conversion internally. Retained-memory and over-target readouts use the same MB label. Approximately 2 GB steady application memory and 4 GB peak application memory remain measurement goals rather than guaranteed allocator limits.

Profile every retained memory owner, including working photos for every edited photograph, processing checkpoints and parameter tables, delivered images, browser thumbnails/previews, shared preparation, speculative preloads and temporary rendering resources. Count shared allocations once. Actual-use recency must remain distinct from speculative loading. Prefetch alone must not promote an entry above genuinely used photographs.

The multi-edit count limit is a separate user setting within the memory design. Determine the interaction behavior first. Admission and eviction follow the [Scheduler](./render-scheduling.md#admission-and-width) and must not be inferred solely from the Thumb pixel count.

## CPU execution

Parallel CPU processing must use the host's available logical CPUs through a shared processing pool. CPU capacity and the number of simultaneously retained source buffers are separate limits. Foreground and speculative work retain their priority and cancellation rules. GPU execution and disk I/O keep separate owners. A dependency-bound stream or serial recipe walk need not invent parallel work solely to occupy every core.

## Per-photo viewing

Each photograph must retain its own Fit or fixed zoom and pan during the application session. Single and multi-photo views must use the same transform and gesture implementation. Selection changes, tile reordering and leaving or rejoining the displayed set must preserve photograph identity. Double-click toggles the hovered photograph between Fit and the application’s zoom snap, preserving the existing pointer-anchor behavior. Pointer drag or temporary Space pans only the hovered photograph without changing editing selection. Temporary Space preserves the selected tool and suppresses viewport selection. Explicit preview modes keep their requested processing scale through these gestures. Smart may resolve a different scale from the photograph’s drawn pixel demand.

With multiple viewport editing targets, Shift viewing gestures on a blue photograph must apply to all editing targets. Shift-drag applies the same on-screen displacement to every editing target, independently of photograph aspect ratio or zoom. Shift-scroll or pinch applies the same zoom multiplier to each photograph’s own view, preserving its own point at the same relative position within the displayed photograph region. Centered input must keep every photograph centered on its own current view. Shift-double-click chooses one common Fit or configured zoom-snap destination from the clicked photograph’s initial mode, including its resulting relative center. It must preserve editing selection even on the first click. Shift-click on white photographs and captions retains range selection. Unmodified gestures remain local. Group viewing must use the existing per-photo transforms and render demand. Undrawn selected photographs retain viewing intent until usable geometry arrives. Previously drawn targets use their last displayed geometry while hidden. Never-drawn targets use whole-image anchor fractions and retain unresolved Fit zoom and on-screen pan offsets until their first usable layout. They must not borrow another photograph’s image coordinates.
