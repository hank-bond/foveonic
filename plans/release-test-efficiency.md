## Design

Extend existing runners. Rust owns application behavior, render graphs and numerical work. Python owns finite job scheduling, process lifecycle and reports. Keep the existing scenario/case declarations and independent assertions. Introduce no general action language, alternate application runtime or remote orchestration service.

Correctness groups may share a host within an explicit memory budget. Each group owns separate input paths, settings, sidecars, cache namespace and evidence. The coordinator declares the complete expected case set before launch and alone combines results. Resolve conservative case-family and fixture worker-memory hints before staging, with an explicit command-line guard taking precedence. A custom fixture requires an explicit guard when concurrency is requested. Workers write disjoint evidence. Performance remains a separate exclusive phase with new matched observations for both released and candidate apps.

Process ownership must be explicit across quiet checks, memory guards and cleanup. An owned worker starts in a separate OS session and launches its native app, monitor and verifier into that same process group. Registration completes before work starts. Only exact declared binaries in a registered live worker's session may be authorized peers. Unrelated app/build workloads remain visible and block the run. Concurrent correctness records never become latency baselines.

Reservations control admission throughout each group's app and verification lifecycle. Sampled memory guards are operational stops, not a machine memory guarantee. Preserve headroom for the operating system and workers. A guard stop remains a capacity outcome. Unknown assertion, image, I/O or process failures remain failures. Do not turn them into retries or lift limits silently. Abort stops admission, cleans verified owned children and escalates after a deadline. A surviving coordinator reaps workers. Surviving workers detect controller loss, clean and reap their own children and exit. Unverifiable ownership or incomplete cleanup fails the run and blocks new work. This does not promise cleanup by a controller that has already died.

Use finite scenario queues, explicit starting-state checks, seeded actions, readiness predicates and complete reset/cleanup. These fit the existing app harness. Persistent verifier processes may retain immutable device/kernel resources while constructing fresh graphs for each request. Application reset changes require measured benefit and equivalence checks. Cold startup, shutdown, restart, source-loading and cache-policy tests keep their declared boundaries.

## First slice validation

The first slice changes Python orchestration only and initially supports concurrent groups on macOS. It adds three focused responsibilities: pure resource admission, process ownership/cleanup and finite group scheduling/evidence aggregation. Existing native slider behavior and independent verification remain unchanged. A separate Sol reviewed the implementation and the paired Sol independently compared native evidence. Review corrections reject failed raw native terminals hidden by summaries, preserve assertion failures when memory stops race with them, and tolerate a process group exiting immediately before cleanup signals.

On the prepared 32 GiB M1 Pro, a maintained CLI pilot selected Classic and Quattro, exposure forward/scrub, dark theme and both processing qualities: eight cases in four application groups. Serial and four-worker runs passed the same eight cases. Independent comparison rehashed every native and fresh floating-image file, finding identical corresponding bytes, geometry, final settings and starting recipes. Workload observations confirmed four simultaneous owned applications, no foreign workloads and invalidated performance timings. The cohort closed with no registered workers. A timed repeat took 40.665 seconds serial and 13.828 seconds concurrent, approximately 2.9 times faster for this selection. This is correctness wall time, not an application latency comparison or a complete release-duration claim.

Native failure probes used two workers and four declared groups. A 1 MiB guard stopped work without retrying. Early probes exposed startup system-information helpers that briefly outlived their worker before a sample established ownership. Cleanup now signals birth-verified remnants promptly and allows unanchored remnants one fixed two-second deadline to exit naturally. It records that outcome and still blocks cleanup if any remain. Repeated guard and controller-SIGINT probes stopped admission, left the two pending groups unrun, emptied cohort registrations and recorded no cleanup failure or surviving owned process. Controller SIGKILL during fresh verification left the dead controller's aggregate incomplete and descriptor active, while surviving workers recorded aborted receipts, cleaned their children and exited. Each probe returned nonzero. A dead controller cannot finalize its evidence. Missing terminal completion must remain a failure for consumers.

The first-slice checks pass: 232 profiling unit tests, six artwork tests and 35 supporting-script tests. One existing captured-trace integration test was unselected because no trace directory was supplied. No Rust or shader inputs changed. Index and whitespace checks accompany the slice.

## Stopping criteria

Further simple group-ordering models do not improve the observed schedule. Within-case preparation reuse gave no measured gain and was removed. One independent oracle source could avoid repeated decoding in a core test, but its effect on source lifetime and memory needs separate review and there is no trustworthy elapsed-time attribution for those decodes. Batching the numerical matrix would need shared camera-default resolution and new evidence handling. A single Metal observation suggests approximately 34 seconds of initialization could be removed, not a demonstrated matrix gain. The evidence does not justify those additional mechanisms now.

The prepared two-Mac schedule remains a model: one host runs required Rust checks and the other 47 native jobs, while the 32 GiB host runs sliders, packaged smoke and exclusive performance. Windows and existing CI run alongside them. Include input staging, compilation, package availability and report merging before taking the longest dependency path. The primary Mac was occupied by unrelated work during this attempt, so this complete parallel path has not been measured. The measured slider span plus exclusive performance alone totals 30 minutes 24 seconds before build, staging and packaged smoke. A roughly thirty-to-thirty-five-minute prepared-host path is a conditional estimate. An end-to-end thirty-minute release run has not been demonstrated. Hosted cache effectiveness also awaits an approved committed workflow run. Ordinary Windows workspace time includes substantial compilation needed by the required tests. Crediting equivalent CI test execution cannot remove that local compile cost. Do not subtract the documentation-test saving again after already removing that execution from a projection.

## Planning sources

[Epic's automation guidelines](https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-test-framework-in-unreal-engine) emphasize explicit starting state and cleanup across reordered or parallel tests. [Gauntlet](https://dev.epicgames.com/documentation/en-us/unreal-engine/gauntlet-automation-framework-overview-in-unreal-engine) separates process orchestration from application-side test behavior. Borrow those boundaries rather than introducing that framework here.

[Rust's test guidance](https://doc.rust-lang.org/book/ch11-02-running-tests.html) warns about shared environment/files during parallel tests. [Nextest's process isolation](https://nexte.st/docs/design/why-process-per-test/) and [bounded test groups](https://nexte.st/docs/configuration/test-groups/) are candidates for later Rust-test sharding, not dependencies selected for the first slice.
