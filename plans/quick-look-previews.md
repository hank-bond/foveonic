# Quick Look previews

Implements [Quick Look previews](../docs/specs/quick-look-previews.md). Released in 0.9.2 together with one source of a photograph's defaults, which the preview needs and which the [coherence cleanup](./coherence-cleanup.md) had planned for 0.10.0 (owner, 2026-11-25). The rest of the related command-line and export cleanup stays in 0.10.0; see [what 0.10.0 takes over](#what-0100-takes-over).

## Probe findings

A throwaway sandboxed preview extension called the engine through a C interface on an Apple M1 Pro with macOS 26. It rendered camera-default Merrill photographs at native size with Speed quality and returned a JPEG reply.

- Metal is available inside the sandboxed extension. Only the app-sandbox entitlement was needed. An ad-hoc signature registered and ran locally.
- Each preview started a new extension process. Engine creation cost 280–310 ms every time.
- Native-size totals were 554 ms (Low), 796 ms (Medium) and 1168 ms (High). Rendering took 165–472 ms and JPEG encoding 60–273 ms.
- Peak physical footprint reached 685 MiB (Low), 1.1 GiB (Medium) and 1.8 GiB (High) without the extension being terminated. Outside the sandbox, High at half size peaked near 0.9 GiB, with about 630 ms expected in total.
- Apple's raw support is a private system bundle with no public plug-in point. Legacy `.qlgenerator` plug-ins no longer load on macOS 15. A warm background helper could remove per-preview engine startup but adds a resident process. It is deferred until extension timings show the need.

## Slice 2: one source of a photograph's defaults

Replaces the coherence cleanup item of the same name. Agreed with the owner on 2026-11-25.

As Shot is one of the white-balance and color-mode options the engine offers. Callers choose an option or leave the default, As Shot. Only the engine knows which preset As Shot means for a photograph. The GUI does not need to know.

- [x] **The engine lists the options.** `ControlCapabilities::white_balance_options` and `color_mode_options` list As Shot first, and `option_label` names each option. As Shot is `render::AS_SHOT`. The GUI menu and the multi-photo availability check use these lists. The GUI's own As Shot entry and its two list sources are gone.
- [x] **Render resolves As Shot.** `Settings::with_camera_choices` names the presets. `prepare_recipe` calls it beside `resolved_exposure`, so every render path gets concrete names and recipes do not change. Artifacts and images keep the requested As Shot, so the decoded-preview cache still matches the saved recipe. `dng::write_source` resolves once at its entry for the profile name and appearance. Automatic ColorDQ and Merrill's automatic sharpening resolve where they read the white balance. Resolution never fails: a choice the file did not record usably stays As Shot, so inspection outputs that do not use it still render, as before. `validate_for_camera` reports "As Shot is unavailable … Choose a preset" only when the rendering uses that choice. The first full GPU run caught the earlier strict version failing Quattro and Classic inspection outputs.
- [x] **Delete the other translations.** Removed from the render worker (twice) and its separate defaults-error channel, presentation (twice), preparation, the toolbar's export check, multi-edit automatic values, `decode_cache/previews.rs`, GUI export, Quick Look, the CLI's Quattro-only fill and the `profile_editing` example. `resolve_camera_choices` is deleted.
- [x] **Keep the stored form.** An empty string still means As Shot, so sidecars, presets and multi-edit's JSON-pointer edits are unchanged. The typed choice waits for 0.10.0's `Settings` split.
- [x] **The command line starts from camera defaults.** `parse_settings_for_camera` parses the options onto `camera_settings`, once to learn the chosen rendering and once onto that rendering's defaults. `--wb` and `--mode` are optional. The `--rendering`/`--mono-*` pre-scan, the reparse from `Settings::new("", "")`, the Quattro-only choice fill and `Settings::validate` are gone. Noise controls a flag edits are filled from the camera's `default_noise_controls_for_metadata`, which reads Quattro's recorded values. The profiling examples start from `camera_settings` and keep their fixed Sunlight and Standard choices.
- [x] **Sidecar noise reduction.** A Merrill recipe without noise controls gets the camera default, noise reduction on, when it is normalized for its family. The app saves the normalized recipe back. This includes 0.3.0 and 0.4.0 sidecars, which saved an off checkbox as missing controls: the owner decided on 2026-11-25 that missing means default. An explicit off, stored as controls with noise disabled, stays off. Classic keeps its own toggle, since it has no noise adjustments, and Quattro leaves missing controls to the file's recorded values.
- [x] Keep `--reconstruction` in the Merrill render cases. It changes nothing on this revision, but comparable runs drive earlier revisions with the current cases, and 0.9.x and earlier would otherwise measure Merrill without noise reduction. Drop it once no compared revision predates 0.9.2.
- [x] Update the [despeckle spec](../docs/specs/despeckle.md), the CLI help and the changelog.
- [x] The test-inventory planner accepts the Quick Look library's two kinds (`staticlib` and `rlib`) as one library test target. Slice 1 had made planning fail.
- [x] Consolidation pass (owner request, 2026-11-25). Recipe building shares one `recipe_settings` step (camera choices, Auto exposure, family processing) between `prepare_recipe` and reduced preparation. The automatic ColorDQ and sharpening values share `Settings::noise_couplings`. `validate_for_camera` asks for a recorded preset only when As Shot is used, and resolution never fails. The color guide resolves its fallback mode through the same function. `EncodedImage` carries its extent, `output::write` takes it whole and is the one place encoding options are validated, and the PNG writer reuses the shared sample reader. One `parse_args` serves the CLI and its tests. Engine-only lookups (`apply_capture_defaults`, recorded choices) are crate-private.
- [x] Review fixes. Reduced preparation (`sensor_data_graph`) built recipes without resolving As Shot, so a default Merrill photograph failed in reduced views and prefetch ("unavailable white balance"); it now resolves through the same function, with a GPU check that a reduced As Shot render equals the recorded presets. The CLI and two profiling examples again fill Quattro noise controls a flag edits from the file's recorded values, as the app does, with a unit test. The recipes' own As Shot fallbacks (Quattro photographic and DNG, the color guide) and the Merrill monochrome capture default that stored "Standard" are removed. `default_white_balance` and `default_color_mode` are crate-private.

Checks: As Shot renders the same TIFF and DNG bytes as the recorded Sunlight and Standard on a Merrill photograph, and the CLI default render matches `--reconstruction`. A unit test shows the CLI starting from the app's camera defaults, including recorded Monochrome.

Accepted cost: an As Shot render and an explicit preset with the same value are different settings, so switching between them renders again (owner, 2026-11-25).

## Slice 3: thumbnails and fallback

- [x] **Build GPU pipelines on first use.** Measured 2026-11-25 on the M1 Pro in fresh processes: the GPU adapter and device took about 20 ms, and building all 316 pipelines at engine start took 253–256 ms with Metal's cache warm and 1640 ms on a new build's first run. `Gpu::pipeline` now builds each kernel's pipeline the first time it is asked for, from shared shader source text kept as `KernelSource`. One lock serializes pipeline building, including the color-field group, because wgpu 25 keeps one error-scope stack per device across threads. The app still builds every pipeline behind its startup screen through `from_device_progress` (owner, 2026-11-25); the CLI, Quick Look and tests build lazily. A GPU check, `every_kernel_pipeline_builds`, builds them all so shader errors still fail. Half-size Merrill High preview in a fresh process, before and after: engine 268–274 ms → 17–19 ms; whole preview 574–590 ms → 324–338 ms with Metal's cache warm; a new build's first run 6.1 s for the engine alone → 770 ms for the whole preview. The background helper is not needed for now.

- [x] Orientation of embedded images moved into `foveonic::preview` (`Preview::upright_linear`, `upright_native_extent`); the GUI's browser thumbnails and previews use it and apply only editing rotations. Framing selection was already in core; its three copies of the same-framing check are now `Preview::matches_raw_framing`.
- [x] Thumbnail extension. `preview::read_at_least` uses the small embedded image when it reaches the requested size, otherwise the full-size JPEG if it shows the Raw's framing. `EncodedImage::from_linear` packs it, so both extensions share one C hand-off and one Swift image wrapper. xtask builds both from one table, and release signs every extension in `PlugIns`. The 12 example files carry a 160–221 px image (1–2 ms) and a full-size JPEG (25–210 ms). Checked through `QLThumbnailGenerator` at 512 px: four files in 1.2–1.5 s together on a cold start, upright, with DP0 using its small image.
- [x] Fall back to the embedded preview when rendering fails. A render that panics, as a lazily built pipeline does on GPU validation failure, also falls back.
- [x] Owner testing in Finder found thumbnails drawn into a quarter of the tile on a Retina display (2026-11-25): Quick Look's thumbnail context is in pixels, not the points of `contextSize`. The extension now fills the context's drawable area; a 2x request returns a filled 1024 px image.
- [x] Review fixes: the GUI releases the decoded embedded image before making display copies again (as 47da59b intended); a poisoned pipeline build lock no longer fails every later build; `Gpu::from_device` cannot fail; xtask's extension table carries whether an extension is data-based; a GUI test that repeated core's orientation test is removed.
- Follow-ups left as they are (review, 2026-11-25): `read_at_least` opens the file twice and, for DP0 above 160 px, decodes the cropped full-size JPEG only to discard it; choosing by size and framing from the section headers in one pass would avoid both. The browser's cache selection and `read_at_least` each write "the full-size image if it shows the Raw's framing, else the small one"; the framing test itself has one owner. The space-bar preview otherwise always renders the raw: a Quick Look reply is one image, so it cannot show the embedded JPEG first and replace it (owner, 2026-11-25).
- [x] The Quick Look checks name tracked photographs instead of reading `MERRILL_X3F`.
- [ ] Measure timings and peak memory for each Merrill size in the packaged extensions.
- [ ] Owner testing in Finder, Spotlight and the space-bar preview.

## Slice 4: capture details in Finder and Spotlight

Owner, 2026-11-25: in 0.9.2, with one owner of capture details.

- [x] **One owner of capture facts.** `CaptureFacts` (core, `capture_facts.rs`) resolves camera, lens, focal length, f-number, exposure time, ISO, exposure bias, program, metering, serial, firmware and date once: the camera's embedded EXIF first, then X3F properties. `MetadataSummary` carries it. EXIF export, the app's information panel and footer, and the browser's columns and sorting all read it; before, export and the panel each read the property keys with different rules, and the browser sorted on raw keys. Agreed combination (owner, 2026-11-25): export's sources and fallbacks, plus the panel's bracket-aware compensation through `CaptureExposureCompensation`. Lenses (owner, 2026-11-26): the camera's own EXIF name, otherwise a description from the recorded focal and aperture ranges ("30mm F2.8"; a zoom such as "24-70mm" omits the f-number), otherwise none. X3F records one widest aperture, which on a variable-aperture zoom may hold only at the focal length used, so a name keeps the f-number only for primes and the exported lens specification fills a zoom's widest-aperture slot only for the end it was shot at, leaving the other unknown (0/0). The name and the specification come from one parse of the ranges (`LensRange`); before, the specification had its own parser that rejected reversed and single values and wrote the narrowest aperture as the long end's widest. X3F records a numeric lens ID that Sigma reused across lenses, so no ID table is kept; the panel's two hand-written names and ExifTool's table were considered and declined. Exported files change in two ways, each with its own test: lenses are described instead of written as IDs, and a bracketed frame records its own exposure bias. Processing recipes still read the raw values the reference software uses, which are processing inputs, not displayed facts.
- [x] **Spotlight importer.** A classic `.mdimporter` in `Contents/Library/Spotlight`, written in C after Apple's template, calls `foveonic_ql_capture` and fills the standard `kMDItem` image attributes. Apple's Core Spotlight documentation states that Spotlight File Import extensions don't provide functionality in macOS; a `CSImportExtension` was built first, registered, and was never given files (the `mdimport -m` harness could not read them either). xtask owns the plug-in factory ID for both the C build and the Info.plist. `mdimport -t -d2` returns the full set for Merrill and Quattro files. Spotlight discovers importers in apps under `/Applications` on its own; a build elsewhere needs `mdimport -r <importer>`.
- [x] Review fixes. `CaptureExposureCompensation` holds f64, so "+0.30" exports as exactly 3/10 again (it had become 5033165/16777216); its validity range stays the f32 range processing applies. A bracketed frame without `EXPNET` records no bias, since its offset is unknown. The panel takes the browser's resolved summary instead of re-reading facts every frame, and the footer readout formats facts directly. The importer reads dates in the Gregorian calendar whatever the user's calendar, and checks every allocation. Unused C fields are gone, and a size check ties the C and Rust layouts. DNG's camera serial and export's EXIF-version check read the facts. Embedded DateTimeOriginal now also supplies IFD0 DateTime and DateTimeDigitized where the camera's EXIF lacks them.
- [x] **X3F is exported as a camera raw image** (owner, 2026-11-26). Finder shows capture details only for types that conform to an image type: `MDSchemaCopyAttributesForContentType` gives X3F only Keywords, Where From and Last Used while it is plain data, and the full camera set as `public.camera-raw-image`. Importer schemas no longer choose what Finder displays (Apple's own Mail importer shows the same), so the schema only declares the custom `org_foveonic_exposure_bias` attribute, with an English label. SIGMA Photo Pro exports the type as plain data and an exported declaration outranks an imported one, so the app exports it too. Tested on the owner's Mac with SIGMA Photo Pro installed, with the app in `/Applications`, signed and launched once: export made ours the active declaration and Finder's gallery panel and Get Info showed the details; import, under the same conditions, left SIGMA Photo Pro's active and Finder showed none. Finder caches file types until it restarts. Costs accepted: Finder offers Convert Image, which cannot decode X3F and writes an empty file, and which exporter macOS prefers is undefined, so SIGMA Photo Pro may take the type back after it is reinstalled.
- [x] `cargo xtask bundle` ad-hoc signs the finished app; Spotlight would not load the importer from an invalidly signed app. The test workflow no longer signs separately.
- [x] Owner check of Finder's gallery panel and Get Info for indexed X3F files (2026-11-26).
- Follow-up: the importer and both extensions each link the whole engine (31–34 MB apiece). The thumbnail extension and importer need neither the GPU nor rendering; a library without them would shrink the app.
