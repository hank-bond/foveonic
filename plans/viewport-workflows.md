# Viewport workflow architecture

Requirements under review: [viewport workflows](../docs/specs/viewport-workflows.md), [Smart preview](../docs/specs/smart-preview.md), [multi-edit](../docs/specs/multi-edit.md), [small previews](../docs/specs/small-previews.md) and [render orchestration](../docs/specs/render-orchestration.md). Apply the [three architecture goals](../docs/specs/render-orchestration.md#agreed-goals) to each slice. The owner approved the preview-quality slice. Later slices remain discussion until individually agreed.

## Checkpoint and review

`02104b4` groups browser sources mechanically. `33453b3` separates requested source loading from serial rendering. Their validation is recorded in the [runtime plan](./render-runtime.md#source-loading-checks-and-lessons). The owner requested an Astra review devoted to architecture before implementing the next viewport features. The review inspected current sources and documentation and introduced no runtime changes.

The existing coordinator, source loader, processing sessions and immutable presentation resources are useful boundaries. This roadmap does not require a new scheduler framework, a universal cache manager or stage-wide engine execution. Wide rendering remains a [separate future experiment](./wide-rendering.md).

The owner approved separating [viewport, visible region and requested render region](../docs/architecture/concepts.md#viewport-and-image-coordinates). Use those meanings consistently. Zoom and pan derive an image-space visible region from UI-space viewport geometry. Follow the [working instructions](../AGENTS.md#work-with-the-owner) for the required review subagent and owner testing at each functional change.

## Proposed review slices

Review names and behavior with the owner before implementing each item. Preserve one supported path as callers migrate.

1. **Resolve preview quality in one place.** Use one ordinary policy function for single and multi-photo requests. The owner replaced the initial count thresholds with physical pixel demand and approved trying that directly. Resolve explicit mode versus Smart, physical display sampling and native-detail intent. Keep camera-specific scale resolution in core capabilities. Remove the scattered promotion decisions rather than wrapping them with another override. Start with quality-policy unit cases and targeted headed mode/zoom checks.
2. **Give photograph viewing state one home.** UI owns per-photo Fit/detail, zoom and pan, keyed by photograph identity. Single and multi-photo drawing use that state. Layout produces viewports and display order without deciding render quality or reading files. Visible regions derive from each photograph's transform and viewport. Pointer/Hand interaction and double-click behavior can then share a consistent gesture path.
3. **Unify single and multi-photo control paths.** Treat one photograph as a one-member photo set wherever the behavior can share a flow. Consolidate selection-independent drawing, quality demand and request handling incrementally. Preserve genuine differences for active tools, inspection, Before and detail consumers. The owner requested this soon after viewing-state ownership. This does not introduce wide execution or replace the scheduler.
4. **Move refinement sequencing to coordination.** UI publishes the needed visible/detail region. The coordinator requests useful rendering and handles replacement, independently of UI paints. Region completion may settle without a Full continuation. Preserve existing engine region capabilities and immutable image retention.
5. **Share detail requests with the loupe.** Start with one replaceable detail request per photo through the existing detail target. Reuse compatible Full or regional pixels by identity, edits, coverage and sampling. Circular clipping is display work over a rectangular rendered region. A loupe may replace uncovered detail demand while the zoomed tile keeps its completed compatible image. Do not union distant rectangles automatically or create a generic consumer registry. Simultaneous fresh refinement of two disjoint regions in one photograph is deferred unless demonstrated necessary.
6. **Choose retention from measurements.** Measure decoded disk loading, native RAM reuse, native preparation, region rendering, optional whole-image work and presentation separately. Only add byte-bounded native source retention if materialization is the relevant bottleneck. Keep native samples out of source-free reduced sessions. If reconstruction or retained Full output dominates, decoded-RAM caching alone cannot solve it.

Aspect-aware layout is a largely independent UX slice after stable per-photo viewing state is established. Avoid expensive permutation searches during UI drawing. Optional idle source acquisition through the loader is another separate ownership slice whose admission and foreground yielding need review together.

## Evidence required

- [ ] Quality matrix across explicit modes, Smart pixel-demand thresholds with one through eight displayed photographs, Fit/detail, selection and framing. Use actual photograph geometry rather than either selection count. Verify explicit reduced modes do not promote, while the loupe still receives Full.
- [ ] Layout and interaction checks with mixed aspect ratios, reorder, preserved selection, persistent zoom/pan and double-click Fit restoration.

- [ ] Regional/full equality for supported recipes and correct whole-image fallback for unsupported ones. Reduced-region execution remains unimplemented until its measured benefit justifies that engine change.
- [ ] Repeated A/B native-detail switching from retained Full pixels, a resident native session, a source-free reduced session plus disk cache, and an original read. Include active Adaptive Tone and representative camera families.
- [ ] Memory for sources, processing checkpoints, Full/region outputs and display textures, including replacement overlap and low-budget behavior. No silent quality downgrade to meet an unmeasured memory assumption.

The first discussion is the unified quality policy and its vocabulary. Measurements can establish a baseline for detail recovery without changing caching policy. No whole-image continuation heuristic, additional source cache or loupe implementation is selected by this review alone.

## Pixel-demand implementation slice

The shared policy chooses among the existing four processing levels, selecting the coarsest with at most 1.5 physical display pixels per sample. The limit is provisional, not a universal perceptual threshold. AMD’s [FSR 1 quality modes](https://gpuopen.com/fidelityfx-superresolution/) use 1.3× and 1.5× per dimension as high-quality engineering presets, but use a different display filter and do not establish photographic equivalence. [ImageMagick’s filter comparisons](https://usage.imagemagick.org/filter/) discuss the sharpness, blur and ringing tradeoffs. This slice retains the existing bilinear display interpolation. Sensor-layer area means are unchanged.

The UI records each photograph’s effective Smart level from current drawing geometry. Initial unknown geometry temporarily requests Fast. Comparison tiles and single-photo views derive sampling from actual drawn image bounds and native composition extent, excluding captions and letterboxing and including zoom and final output resize. Per-photo request state observes policy and effective quality independently of edit dirtiness. Existing request matching compares the concrete level, and presentation reuse must reject pixels coarser than Smart demand. A completed finer Smart image can remain useful without recomputing unchanged pixels. Explicit modes require their selected grid. Composition retains its existing pixel-reuse exception.

Smart’s resolved reduced requests now use the same source-free reduced sessions as explicit qualities, rather than routing all Smart overviews through the single native session. This is intentional for multi-photo reuse. Native detail reacquires its source on demand, and region-to-Full reuse remains with the existing native session. This slice introduces no decoded-RAM cache or new retention owner. Initial detail acquisition latency remains distinct from warm regional continuation.

During the quality-only slice, only editing targets requested fresh processing. Retained non-editing tiles kept their completed pixels until reselected, even after their desired Smart level changed. The owner accepted this temporary limitation and selected the separation implemented below as the next focus. Refreshing all thumbnail-only photos still needs explicit source admission and memory policy.

The largest available review subagent approved code design, cleanliness and Rust practice after fixes for scale sufficiency, Before preservation and quality-independent numeric defaults. Validation passed 463 GUI unit checks, 126 portable profiling checks and strict GUI Clippy. Native checks passed fresh two-photo Draft and eight-photo Fast sets with editing readiness, an eight-photo transition journey including fixed Draft/Thumb zoom and Smart Before zoom, and the Smart refinement/crop/reopen suite. GPU regressions verified concrete Smart resolution upgrades against fresh processing and composition reuse without photographic dispatches. All 40 frozen numerical cases remained bit-exact. No display-filter or core processing arithmetic changed.

The broad native transition checks assert the active photograph’s scale. Fresh fixed-quality group checks cover every editing target. They do not independently assert automatic quality refresh for inactive tiles. The owner reviewed the basic Smart behavior, accepted it and approved committing this slice. The rendering-demand separation is recorded below. Layout, persistent per-photo zoom, Pointer/Hand consolidation, coordinator-owned detail sequencing and the loupe remain later slices.

## Separate rendering from editing selection

The owner approved this next slice after accepting and committing pixel-demand Smart. The current photo runtime remains the bounded owner of settings, metadata and completed images. Its editing paths control relative edits and readiness of shared controls. Its render paths include editing targets plus actual layout members already present in that owner. The UI publishes actual displayed paths after layout. Thumbnail-only unknowns do not enter the owner. No new scheduler, source cache or admission policy is introduced.

One render-path snapshot feeds preview-quality observation, complete ready request snapshots, coordinator retention, published view context and the UI’s final delivery check. Retention publishes after layout and selection handling, including history eviction. It must not issue a change command on every paint. Rendering does not require multiple editing targets or wait for unresolved siblings. Pending members stay dirty until their settings arrive. Sidecar observations cover the existing bounded owner so browser-scoped paste cannot make inactive refreshes use old edits.

The overview submission reports whether it actually submitted the active photographic view. Other refreshes must not intercept Camera/Defaults, inspection or native-detail submissions, or clear active Smart/detail state. The active inspection/comparison path is excluded from ordinary overview requests and remains dirty for a later ordinary photograph request. Newly added render demand becomes dirty so hidden canceled upgrades restart on redisplay. Existing compatibility and presentation reuse decide whether processing is needed. Single-photo rendering retains its existing submission path.

Native checks exposed a separate ownership gap on inspection exit: the coordinator could coalesce a completed photograph while the UI no longer owned its frame. Non-photographic whole-frame replacement now retains the prior photo in the existing owner. Normal and covering-overview submissions restore compatible photographic frames with the same processing identity and a new presentation revision. Selection and restoration share compatibility checks. Inspection buffers do not supply photographic quality geometry.

Validation passed 468 GUI unit tests, strict GUI Clippy, formatting and document checks. Native checks passed all-tile quality changes with one editing target, Before/inspection preservation, both ordinary and covering-overview photographic restoration with unchanged processing identity, held selection, source loading and cached switching without numerical dispatches. Sixteen final app-image comparisons across the two eight-photo scenarios were exact against fresh processing, and all 40 frozen numerical cases remained exact. The single-photo Smart refinement/crop/reopen suite also passed. The largest available review subagent approved the final design and Rust implementation. ## Mixed-scale Smart editing investigation

The owner reported that four selected editing targets become slower together after zooming one photograph. The transition journey now measures three settled group exposure edits in Fit, three with the active photograph at 200%, and three with the same layout and zoom but only that photograph selected for editing. The setup uses the viewport selection command API, since repeating browser Select All does not replace an explicit viewport subset. Per-photo observations run before the global worker-busy check, record actual processing scale and task identity, and distinguish first current feedback from complete group settlement. Exposure actions use direct application commands. This is not a physical slider-drag measurement.

On the four mixed-camera scenario inputs, an untraced run with the then-default 1 GiB retained-memory budget measured 57–59 ms for the three Fit group edits, versus 972–1380 ms for the three mixed Full/Thumb group edits. All four remained editing targets. Only the zoomed photo used native processing. The other three stayed at divisor 8. The same-layout single-target control took 1186, 348 and 49 ms as its native cache warmed. These are diagnostic samples from one run, not stable benchmark percentiles.

A separate Perfetto run reproduced the slowdown and showed repeated decoded-cache loading, rebuilding of discarded native graph checkpoints, eviction of the reduced working sets under the shared budget, and serial queue delay. Individual photographs can still reach the UI before the group finishes. There is no evidence here of a group-wide presentation barrier. Cache eviction explains why some reduced renders also perform fresh preparation rather than only waiting.

A second traced run with a 4 GiB diagnostic memory budget had no processing-session evictions during these edits, but still reacquired native input and started the native graph with zero retained checkpoint bytes on every mixed group edit. The same-layout native-only control retained approximately 836 MB of native checkpoints, required no source loads, and completed its three edits in 51–66 ms. Increasing the budget therefore does not resolve the ownership problem.

The existing reduced-photo renderer unconditionally takes and discards the worker's native session after a successful cached reduced render, including a different photo's session. This creates an implicit native-or-reduced ownership choice even though the current memory accounting already handles both owners together. The proposed first fix is to retain compatible native and reduced sessions together and release them through actual replacement, clearing and the existing memory policy. Reprofile before changing scheduling or introducing a new cache owner. All three native runs passed their declared behavior checks. The final 471 GUI unit tests, strict GUI Clippy, formatting and document checks passed. The largest available review subagent accepted the test design and attribution, while noting that these samples do not quantify each cause’s exact share. At this checkpoint only tests and profiling had changed. The owner then approved the ownership fix below.

Reproduce with the ordinary `transition-journey` runner, the prepared scenario manifest, four photos, one generated action pair and a single trial. Use `--mode off` for the timing baseline, and `--mode wall --trace-processor <executable>` for attribution. Set `--step-timeout 150`, a named disposable decode-cache namespace and a 1 GiB disk-cache budget. Use `--memory-cache-bytes 1073741824` for that historical baseline and compare with `--memory-cache-bytes 4294967296`. The `scenario.smart_edit` trace events and transition evidence identify Fit versus zoomed trials, editing-target count, individual task arrival and group completion. Clean up only the named diagnostic cache when finished.


## Preserve native ownership during reduced rendering

The owner requested a second opinion, a regression test and a fix. The largest available review subagent confirmed that all three reduced paths had the same lifetime mistake. Cached success, cold acquisition and source recovery must borrow the worker’s native session rather than discard it. `Photos::load` no longer takes an engine, since source lookup has no GPU lifetime decision to make. Both reduced entry points receive an immutable native-slot reference. Source sharing checks origin as well as path. Actual native replacement, explicit clearing and existing shared-memory trimming remain unchanged. There is still one native slot, not a new cache or scheduler.

The new ignored GPU worker regression warms Full A, loads Thumb B cold, alternates three changed Full/Thumb exposure edits, upgrades B to Draft and returns to Full A. It failed the old code with three source loads where two were required. The fixed version keeps the native source and its warm GPU dispatch count throughout the alternations. Only B’s finer-grid upgrade causes an additional source acquisition. Both final outputs match fresh processing byte-for-byte. Related reduced switching/resealing, source-free speculative preparation, explicit clearing and shared Current/Before/picker acquisition tests passed. All 471 ordinary GUI unit tests and strict GUI Clippy passed. The review subagent accepted the implementation and test design.

Real-app checks kept four displayed photos, one at 200%, and all four editing targets. With a 4 GiB diagnostic budget, traced mixed-edit completion improved from 1062–1386 ms to 93–111 ms. The three mixed edits now had zero source loads, zero processing-session evictions and retained native checkpoints on every edit. An untraced 2 GiB run completed the same edits in 96–118 ms. These three-sample runs establish a causal diagnostic result, not stable benchmark percentiles.

The then-default 1 GiB budget exposed a separate limitation. Its untraced mixed edits measured 1007, 673 and 673 ms after this fix. A trace confirms that native source reuse and its approximately 413 MB of checkpoints now survive, but all three reduced working sets are still evicted and rebuilt. Logical retained allocations, frontend reservations and in-flight replacement overlap can exceed this budget even after those evictions. Existing trimming protects the native source and current dependencies, so the setting is not a hard process-memory ceiling. Do not claim that the ownership fix fully resolves default-budget latency or that the native slot itself is evicted by this trim policy.

This ownership fix changed neither scheduling nor eviction order. All 40 frozen camera/quality cases remained bit-exact, and four final app-image comparisons matched fresh processing exactly. The owner reviewed the higher-cache behavior, confirmed it looked good and approved the default change below. A follow-up should still review current editing working sets versus history and replacement overlap before changing eviction policy.


## Approved cache default and final cleanup

The owner approved a 2 GiB default after reviewing the mixed-resolution behavior. Explicitly saved user budgets remain unchanged. The Settings cache field now stores a whole-number MB count and shows all digits through the shared count widget rather than the compact photographic-adjustment formatter. Memory readouts use MB labels with the existing binary conversion. Maximum editing-target counts use the same whole-number widget. The existing thumbnail quarter-share policy remains unchanged.

The scenario runner now defaults to 2 GiB. The acceptance catalog explicitly pairs the four-photo transition journey at 2 GiB with `scenario-smart-low-memory` at 1 GiB. Both exercise independent Smart resolution, mixed editing and the solo control, and record per-photo and group latency. Low-memory correctness does not require the same latency as the normal budget. The low-memory case enables decoded disk reuse to expose working-set pressure separately from source decoding.

The independent final review requested a missing assertion: remember each non-zoomed photo’s settled Fit scale and require that it stays unchanged after the active photo is zoomed. The native journey now enforces this alongside native scale for the zoomed photo. Smart arrival observation and tile-view assertions moved into local methods so the transition sequencer remains readable. No new test framework or runtime architecture was introduced. Final validation passed workspace Rust tests and strict workspace Clippy, including 472 GUI unit tests, plus 127 portable profiling tests, five artwork tests, formatting and document checks. Both explicit 2 GiB and 1 GiB native acceptance jobs passed, including the new independent-scale assertions and eight exact fresh-image comparisons. The 40-case frozen rendering matrix and five focused GPU checks passed during the ownership fix. The largest available independent review found no remaining code or design blockers. The owner approved committing this checkpoint. Broader single/multi control-path unification, layout, refinement sequencing and the loupe remain later slices.
