# User-support logging audit and plan

## Production packaging and follow-up

The owner approved rebuilding and publishing 0.8.2 with the current logging implementation. Public downloads exclude PDB/dSYM files, while matching symbols remain developer artifacts. Resolved production stacks are best effort. Richer logging follows after release, with stable event codes, operation correlation and useful failure context as the proposed focus. Do not expand this release with new symbol lookup, crash handlers or logging architecture. The separate release-process reflection remains pending after publication.

Source baseline: commit `5c68c86` (the pushed 0.8.2 export correction). Read-only Astra planning with eight Terra audit agents, including a rendering/scheduling follow-up. Source locations below refer to this baseline. No logging implementation or repository edits were made by the audit team.

## Decision summary

Build one application-owned support-reporting path that starts before graphics, preserves structured errors before they become UI strings, and supplies both bounded JSONL files and the Log modal. Use shared conventions across subsystems; instrument ownership boundaries, not every `?`.

The purpose is debugging failures reported by users. Exclude performance, latency and memory tracing, scheduling/dispatch event streams, Perfetto integration and future user capture workflows. Static RAM/GPU-memory capacity remains required system context. Timestamps establish chronology, not performance measurements.

Confirmed owner decisions:

- A run is one application launch, including a launch that fails before showing a window.
- Each launch has a dated header and Copy run logs. Copy logs copies all visible retained history.
- Clear rotates the active segment, persists the display/copy cutoff, and clears visible history. Cleared events must not enter clipboard reports. Archives may remain on disk within retention. The same launch ID and its original context survive Clear and automatic rotation.
- Record stack traces for logged errors whenever possible, beyond panic traces. Label where a trace was captured and its limitations.
- The owner subsequently approved logging implementation in 0.8.2. The specification is accepted and implementation is conforming. The audit below preserves the baseline coverage checklist. Final verification is recorded under implementation progress.

## Existing behavior and why merely saving Activity is insufficient

`activity.rs` stores at most 1,000 in-memory string messages, starts after App construction, and silently drops older entries. It does not see early native setup, typed errors discarded by workers, or failures that stale-result/UI filtering hides. Existing performance diagnostics are optional and must remain independent.

The common library result is `Box<dyn Error + Send + Sync>` (`crates/foveonic/src/source.rs:16`). Some custom errors preserve causes, but many handoffs convert them to String. Most ordinary errors do not contain an origin stack. Capturing a stack later in the UI cannot recover the original worker stack.

During this audit the root investigation reproduced a separate released startup regression on the interactive Windows desktop: 0.8.0 completed its smoke scenario; 0.8.1 exited with main-thread stack overflow, status `0xC00000FD`, before captures. This is evidence for early breadcrumbs and honest crash-coverage limits, not evidence that a Rust panic hook will catch stack overflow. The proposed logger is not the startup fix.

## Shared architecture and conventions

### Ownership and Rust interfaces

Use `tracing` as the common structured instrumentation facade in core and GUI code. Install the subscriber once in the executable, never from the library. A small application-owned `tracing-subscriber` layer should convert support events and selected dependency warnings/errors into owned records for one support store. That store owns JSONL segmentation, the retained UI snapshot, cutoff/copy handling, and shutdown. Typed helpers should provide nested recipe/error data without making call sites hand-build JSON strings. Keep core reporting independent of egui, filesystem log paths and window state.

Structured logging dependencies are approved. Use standard crate facilities for event/span context and dependency capture. Keep the application-specific storage policy small. No global runtime migration or new general-purpose logging framework is needed.

| Candidate | Recommendation |
| --- | --- |
| `tracing` + `tracing-subscriber` | Preferred for structured fields and scoped operation context. A custom Layer is the supported extension point for the application's record policy. Do not instrument every function or automatically Debug-print all arguments. [tracing](https://docs.rs/tracing/latest/tracing/), [Layer](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/layer/index.html) |
| `tracing-log` | One-way bridge for selected dependency warning/error targets, particularly graphics/window setup. Unstructured dependency text stays text, and lacks a guaranteed typed cause. Do not bridge events back into `log` and form a recursion loop. [tracing-log](https://docs.rs/tracing-log/latest/tracing_log/) |
| `tracing-appender` | Evaluate rather than assume sufficient. It has a bounded off-thread queue and a drain guard, but the documented generic queue does not supply our error reservation, visible-history cutoff, self-contained launch segments or cross-instance retention policy. Avoid layering two worker queues merely to use it. [non-blocking writer](https://docs.rs/tracing-appender/latest/tracing_appender/non_blocking/) |
| `anyhow` | Do not convert the whole result graph for logging. It is useful application context machinery, but its default backtrace behavior depends on environment settings and it does not recover a stack from a previously stringified error. Existing typed control flow must stay intact. [anyhow](https://docs.rs/anyhow/latest/anyhow/) |
| `thiserror` | Appropriate when adding an actual typed operation error with a source, if it simplifies code. It is not an automatic stable-Rust backtrace solution; its documented Backtrace/provide integration requires nightly. Keep a support-report backtrace separate on the repository's stable MSRV. [thiserror](https://docs.rs/thiserror/latest/thiserror/) |
| `tracing-error` | Defer. Its SpanTrace is logical tracing context, not the requested OS-thread call stack. Existing explicit job context is sufficient initially. [tracing-error](https://docs.rs/tracing-error/latest/tracing_error/) |

### Event and correlation rules

Use a versioned envelope with `launch_id`, sequence, wall time/timezone, severity, stable event name, component, thread identity/name and structured fields. Sequence is authoritative within a launch; wall time can change. Assign/serialize ordering consistently at the common ingestion boundary. Use launch-specific filenames so separate processes never append to one active file.

Carry immutable operation context in requests and completions: operation/job ID, parent operation, source identity/path, revision, purpose and output destination when applicable. Existing coordinator `Stamp` and immutable `Arc<Request>` are useful (`rendering/coordinator.rs:30`), but task IDs may be reused across compatible revisions. Identify work by launch + task + revision, with an attempt only where retry distinction matters. Do not derive support context from the currently selected photo or from capture-enabled thread-local state.

Use a small vocabulary, for example `launch.started`, `context.updated`, `startup.phase_started`, `startup.phase_completed`, `application.ready`, `operation.failed`, `operation.recovered`, `artifact.published`, `service.stopped`, `launch.exited`, and `log.history_incomplete`. Distinguish error, actionable recovered warning, and ordinary control flow. Cache absence, source-not-yet-loaded, supersession, user cancellation and expected missing optional files are not errors.

Record entry/terminal state for explicit user operations and startup phases. For rapid preview work, persist failure reports with the actual request context, not every request/start/success. Keep needed current operation context in memory for reporting and panic breadcrumbs. Record successful artifact publication because it determines what survived a later partial failure. One component owns each detailed failure report; downstream UI delivery references that report rather than emitting another full copy.

### Errors and stack traces

Introduce a narrow owned `FailureReport` at the earliest useful reporting/worker boundary. Preserve the original UI message plus the complete cause chain, attempted operation/phase, paths, structured `io::ErrorKind` and numeric OS codes, immutable job/settings context, and a failure ID. Pass the report or a shared report handle across channels instead of reducing it to String. This can be introduced slice by slice while preserving the library's current result alias and behavior.

Capture `std::backtrace::Backtrace::force_capture()` for real logged failures when no known earlier trace exists. Store capture status, boundary name, thread and reporting source location. `#[track_caller]` identifies the reporting call site, not the original error creation site. Capture before enqueueing to another thread; serialization/symbol formatting may be deferred. Repeated identical failures can reuse the first report with count/last-occurrence updates to avoid repeated expensive captures. Never capture a stack for an expected cache miss or superseded request. The standard API explicitly distinguishes disabled/unsupported/captured states and force_capture avoids requiring the user's environment to enable traces. [Rust Backtrace](https://doc.rust-lang.org/std/backtrace/struct.Backtrace.html)

At selected high-value origins (file publication, source read, device/map/compile failure), preserve typed causes and capture local evidence earlier when it materially narrows the failure. Do not add blanket wrappers around all errors: `Interrupted`, `SourceRequired`, `Superseded` and damage classification have existing downcast behavior. If an upstream API already returns only text, report text plus a labeled boundary trace without inventing a typed cause or origin stack. An async GPU callback's stack is the callback's CPU stack, not the GPU execution stack.

The panic hook should capture payload, thread, location and best-effort trace and retain the previous hook. Its bounded emergency path must not depend on a queue or lock owned by the panicking thread. A small independently writable per-launch emergency record is reasonable; include it in history/copy/retention handling. Do not promise capture of loader failures before `main`, native exceptions, abort/forced termination, allocator failure or stack overflow. Rust's documented hook runs before ordinary panic runtime handling; that does not make every native termination a Rust panic. [Rust panic hook](https://doc.rust-lang.org/std/panic/fn.set_hook.html)

Release backtraces also need matching symbols. The repository has no release debug-symbol policy and current archives do not retain PDB/dSYM artifacts. Plan build identity (version + commit/build ID + target), suitable release debug information, and retention of matching Windows/macOS symbols as developer CI artifacts. Validate actual packaged binaries; do not promise file/line frames from default optimized release builds. This is part of useful error reports, not a performance feature.

### System and settings context

The actual GUI-selected adapter is `CreationContext.wgpu_render_state.adapter` (`gui/startup.rs:327`); the engine receives that same device. Preserve complete available `get_info()` fields, actual device limits/features and display format. List `RenderState.available_adapters` separately. Existing `diagnostic_hardware` (`gui/main.rs:154`) contains only a subset and is not an always-on source. Do not join a native memory query to a selected GPU merely by name/vendor/device: identical adapters exist. Use the selected backend's DXGI LUID or Metal registry ID when exposed; otherwise explicitly mark memory-to-adapter association unavailable.

Collect exact OS product/version/build, CPU model/core counts and physical RAM through a narrow native abstraction or a small appropriate system-information dependency, tested on both supported platforms. Use inventory once, progressively and off the UI path; do not add resource-use sampling or an external-command inventory framework. API/dependency selection needs an MSRV/platform check during implementation. Inventory failure must leave useful startup evidence and explicit unavailable fields.

Windows DXGI distinguishes dedicated video memory, dedicated system memory and shared-system-memory allowance. Metal distinguishes unified memory and a recommended working-set threshold. Preserve those meanings instead of inventing a combined VRAM capacity. [DXGI adapter description](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_6/ns-dxgi1_6-dxgi_adapter_desc3), [Metal device inspection](https://developer.apple.com/documentation/metal/device-inspection)

Record configured DXC selection separately from actual loaded compiler/version when discoverable (`gui/main.rs:2164`). Embed version/revision/target/build identity at build time, with dirty/unknown explicit; do not invoke git at runtime. Preferences and processing options are serializable (`gui/preferences.rs:128`, `gui/processing.rs:11`), but select relevant processing/cache/display fields instead of dumping arbitrary stored blobs or the environment. Refresh context on relevant setting changes; operation reports still own their frozen/effective recipe independently.

### Storage, UI and startup reliability

Proposed defaults remain active segment plus three archives, rotating at 1,000 event records or 4 MiB; cap individual events provisionally at 64 KiB. Retained history is bounded, not necessarily four complete launches. Headers must retain original launch context plus latest resolved context and never claim a segment is another launch. A long operation's failure must include its own effective context even if its start record was evicted. Split bounded context records if required rather than silently dropping indispensable settings to satisfy a single-record cap.

One bounded writer owns serialization and ordinary file I/O. Reserve capacity for important errors/control commands, aggregate dropped counts, and provide bounded shutdown/drain. Preserve final errors on explicit `process::exit` paths; destructors alone do not do this. Write complete lines promptly without synchronizing every routine event. A stalled writer or unwritable directory must not freeze interaction or exit. In-memory UI evidence remains available and reports persistence failure once, without recursively trying to log it.

Start with a small launch record before optional system inventory, profile parsing or graphics. Inventory and loaded preferences progressively enrich the same launch. Graphics phase entry must precede the operation; the existing completion-only timing hook cannot prove which operation hung. Startup failures should identify the documented log path and allow copying useful evidence when UI is available.

The UI consumes immutable retained snapshots; no file I/O in frame updates. Copy visible and Copy run use the same filtered view and expand relevant context. Clear must be serialized with recording/rotation and acknowledge a persisted cutoff, so later events are not accidentally cleared and a restart cannot resurrect cleared messages. Context survives the cutoff; cleared event text does not. Copy/export reports disclose retention, dropped records, truncation, incomplete trailing lines and emergency records. Ensure an in-progress copy has a stable snapshot when rotation happens.

Multiple launches need unique files and protection against pruning another active writer. Keep one documented global archive budget for inactive segments, with active-instance safety. Exact lease/locking and temporary over-budget handling are implementation choices to settle in the storage slice; do not quietly multiply a claimed 16 MiB global budget per launch.

### First-slice interfaces and ownership

The backend lives in `crates/foveonic/src/support/` with its `lib.rs` export. The shared application runtime, subscriber and system collector also live there. The GUI wrapper selects its directory and supplies GUI-specific context. CLI and GUI use the same store. Boundary owners use the same API and do not create their own file writers. Astra reviews each slice and maintains the coverage checklist. Keep simultaneous owners out of the same files.

Expose a small typed API with these responsibilities. Names may be adjusted together before callers are written.

```rust
// Executables initialize once. Library calls remain harmless without a sink.
support::initialize(config) -> Guard;
support::event(level, name, message, fields);
support::update_context(section, fields);
support::report_error(boundary, error, operation) -> Arc<FailureReport>;
guard.snapshot() -> Snapshot;
snapshot.copy_report(VisibleSelection::All | VisibleSelection::Run(id)) -> String;
guard.request_clear() -> ClearRequest;
guard.shutdown(timeout) -> ShutdownStatus;
```

`Guard` exposes persistence/subscriber failure status and the actual log path. Initialization must leave an in-memory store available when disk persistence fails. Tests instantiate isolated stores instead of repeatedly replacing a global subscriber. A `Snapshot` owns immutable run groups, contexts, visible entries and incompleteness notices. Copy formatting consumes that same snapshot. A Clear request is asynchronous and reports completion or failure. The modal clears only after the persisted cutoff succeeds. Shutdown has an explicit deadline and must run before any `process::exit`.

`FailureReport` owns an ID, original display text, ordered cause messages, each available I/O kind and numeric OS code, capture boundary/caller/thread, backtrace status and trace, and immutable operation context. `OperationContext` includes operation ID, parent ID when known, component/phase, source and destination, photo revision/purpose, and the actual frozen settings/options. Serialize preview request settings only when reporting a failure, using the existing immutable request. Do not serialize every slider revision. Export begins with its frozen context and updates effective context after camera resolution and export overrides.

Capture the stack on the failing worker before channel conversion. Formatting/symbol resolution may move to the writer, but the captured stack must not. UI delivery carries the shared report or failure ID and existing readable text. It does not capture another stack. Keep the current core error alias. If a lower boundary must preserve an earlier report through `Result`, use a narrow source-preserving reported-error wrapper only for terminal errors. The reporting helper recognizes and reuses that report. Never wrap `Interrupted`, `SourceRequired`, supersession or other errors whose concrete type controls recovery.

Ordinary structured instrumentation uses `tracing`. Typed failure/context helpers can submit owned records directly to the same sink rather than encoding JSON into tracing strings and parsing it back. ### Bounded storage and concurrent launches

Use unique `<launch-id>-<segment>.jsonl` names created exclusively. Use a sibling ownership lock file for each active segment. Locking JSONL itself can interfere with readers on Windows. Hold the ownership lock for the writer's active segment and never prune a segment whose ownership lock cannot be acquired. Use a short directory maintenance lock to serialize segment creation/pruning and cutoff replacement. Do not hold it while formatting stacks, reading system information or writing ordinary events. Old lock metadata is removed with its segment.

Keep three closed segments globally plus one active segment per live process. Rotate each active segment at 1,000 event records or 4 MiB. A crash releases its OS lock, allowing later maintenance to treat that segment as closed. Failure to obtain a maintenance lock postpones pruning rather than risking another active writer. Report temporary retention excess explicitly. Context header records count toward the byte bound and must be bounded themselves. A long launch retains its original identity, initial context and latest context in each segment.

Use one bounded queue and writer thread, initially allowing up to 512 ordinary entries with a 4 MiB queued-payload budget and 32 reserved error entries. Reserve control-command admission independently. Assign sequence/order while admitting records under one short ingestion lock. Ordinary overflow increments a loss counter. Error overload must also be disclosed, not block processing indefinitely. Maintain a bounded in-memory view even when persistence fails. Avoid a second unbounded copy of formatted backtraces or event payloads.

Clear is an ordered writer command. Persist a versioned map from retained launch IDs to the highest cleared sequence, merged by maximum under the directory lock. Include the current launch's already admitted events. Rotate and retain current context. Then acknowledge the UI change. Cutoff metadata for launches with no retained segments can be discarded during maintenance. Readers apply the same cutoff after restart and copy uses only visible entries. Context is report metadata, so current launch settings remain available even when its old messages were cleared. Concurrent launches never share an append handle. Their snapshots may refresh on modal open, without disk I/O during frame updates.

Persist a minimal launch record before profile/argument parsing or native graphics work. A separately pre-opened, bounded emergency file handles the first panic using a path independent of the normal writer/queue locks. Merge emergency evidence into history and retention. Preserve the previous hook. Failure of this emergency attempt must not recurse. It cannot guarantee a report for abort, stack overflow, loader failure or a stalled filesystem.

Use `~/Library/Logs/<app-id>` on macOS, `%LOCALAPPDATA%/<app-id>/Logs` on Windows, and `$XDG_STATE_HOME/<app-id>/logs` or `~/.local/state/<app-id>/logs` on other desktop platforms. Respect the existing review-build application ID. Failure guidance and the modal expose the actual selected directory. Do not silently place reports in the source-photo directory.
