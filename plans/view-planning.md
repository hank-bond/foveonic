# View planning

Requirements: [view planning](../docs/specs/view-planning.md), [viewport workflows](../docs/specs/viewport-workflows.md) and [Smart preview](../docs/specs/smart-preview.md). Implement one step at a time with owner testing between steps. Part of the 0.9.0 work in the [render scheduler plan](./render-scheduler.md).

## Starting point

Six-photo zoom captures on 2026-11-19 showed:

- After an exposure edit while zoomed, each photo's 1/8 navigator preview and patch had the new edits, but the image drawn behind the patch stayed the pre-edit 1/4 fit image for the rest of the session. The full-size continuation started but never finished.
- A patch render takes 135–250 ms. With six photos, patches ran one at a time, so the sixth arrived after about 1.2 s. The scheduler ran them serially because cached data filled the 6 GB target and a second job may not evict to run alongside.
- A moved region waits as "pending" until the in-flight patch finishes, so the patch for the final position queues behind one the user dragged past.

## Migration checklist

Done: views, planner, rendered images, one reconcile rule, delivery by image in use, and the deletions in steps 1–5 below, including `delivery.rs`, Before staging, the overview path, the auxiliary preview, `Purpose::Detail` (a patch is a target flag) and the coordinator's view snapshot. `views.rs` owns every displayed-photo decision. GUI unit tests, clippy and docs pass; the six-photo zoom workflow and the transition journey pass natively. Remaining: app-level planning tests and the review findings that need owner decisions.

1. **Views.** One `App` function builds every viewport photo's view each frame: key from its look (`photo_rendition`), output and comparison (the active photo's `output` and `comparison`, else final), framing for the active photo while the plane is active; shown from loupe, zoom or framing with settling. The template request carries the look's settings (`Before::settings` for Camera and Defaults, authored settings otherwise), output, comparison, framing and the quality from `quality::for_view`.
2. **One collection.** `App` owns `RenderedImages<Frame>`. Delivery stores every accepted image with `accept`; it accepts a result whose key and request are in the last published images in use. Remove `delivery.rs` destinations, `App::frame`, `multi_edit` frame, detail and preview slots, `Before::saved` and `Before::detail`, `restore_photograph`, `mark_stale` and the Before cache-and-restore code.
3. **Reads.** Every reader of the old stores asks the collection through the view: the drawn whole image and patch for a photo (layer rule), the active photo's image for scopes, navigator, information bar and picks, and the whole image for browser thumbnails. Images not shown by any view stay in the collection only for retained history photos and the other look of a viewport photo; everything else is dropped.
4. **Requests.** `submit_photos` plans every view; delete the overview path, `submit_before_photos`, refinement staging, `submit_with_quality` for displayed views, and the coordinator's retirement rules for viewport photos. Export stays separate.
5. **Clearing.** A worker clear forgets which images are current: images rendered before the clear stay as placeholders but are not ready.
6. **Tests.** Planner rows, the collection, app-level planning-loop tests, then native scenarios.

## Design pass

Agreed with the owner after the migration review. Each decision is made in one place.

1. **Views once per frame (done).** Planning stores each viewport photo's view (its request and how it is shown) in `App::views`. Planning runs after drawing, so a frame draws the views planned at the end of the previous frame. `photo_layers` draws a patch only over a magnified view, and the loupe places only layers with the view's geometry, quality and calibration, so neither derives its own request, zoom check or settings.
2. **No export through the render worker (done).** The app never submitted an export: every export goes through the batch exporter. The worker's export path was dead and is deleted (`submit`, `submit_with_quality`, `active_render_request`, `App::exporting` and the controls it disabled, `Request::export`, `frozen_export`, the host's export job, `Reply::exported`). Export moves onto the shared engine and scheduler as a recipe with an encoder node in slice 10. The footer progress bar shows only view renders, so batch export has no bar (it predates this pass); with export on the scheduler its progress comes from the same tracker. Test gap for that: the deleted worker tests checked that a DNG export reads the original source from any inspection view, and that exports are full size whatever the preview quality or region.
3. **One submission path (done).** `submit_photos` runs every frame, so `submit(None)`, `submit_active`, the `retained_current` block and the preview-density change flag were repeats of it and are gone. The single-request `Worker::submit` remains only for worker tests; move those tests to `plan` and delete it.
4. **One function each (done).** `PixelRegion::bounds` and `native_bounds` convert visible pixels; scopes use `visible_region`. Tile drawing and transform changes both record densities through `observe_photo_view_density`.
5. **Request id (done).** `RenderRequest::id: RequestId` is issued in order, one per image in use, from `App::last_request_id`; a result reads it through its request, and `Stamp`, `ScopeKey`, admission and delivery carry `RequestId`. Conversion to `u64` happens only for timing and progress diagnostics. Adaptive tone tuning is part of the render settings and the calibration signature is matched, so matching already decides what is current: `forget_current` and `current_from` are gone. A patch's id no longer needs to be higher than its whole image's, because they have separate targets and slots and the layer rule keeps an equal-id patch on top; ids stay distinct so progress and scope keys tell them apart.
6. **Names (done).** `RenderRequest`, and `RenderResult` (the delivered image, linked by `request: Arc<RenderRequest>` instead of copying path, look, output, framing, detail, id and calibration). `Reply` reads those through its request too. The collection's `Stored` extends the planner's `Rendered`, so the request id is defined once, and a result is filed under its request's key. Later, as its own step: the core `Artifact` becomes `Render`.
7. **Loose ends (done).** `smart-transition-full` waits for the planner's full-size image; `keep_motion` and `selected_request` replace `moving` and `selected_revision`; the `PhotoImages` and `Use` comments describe the current rules.

Review of this pass: the loupe could stall when the lens had no image of the view's geometry, quality or calibration to land on (after a crop, quality or calibration change), because the photo waited for a lens and so left the views drawing reads. A waiting photo now keeps its last view, and a loupe with nothing placeable renders a whole-photo patch to place the lens. A GPU-free planning test should cover it. Cleanups after the review: the request's `processing_quality` is the single authority on quality, decided by `quality::for_view` (inspection and comparison use Quality) and copied into the request's settings; `apply_preview` no longer repeats the rule. A result reads the quality actually used from its render, and its copied `requested` settings are gone. `Preferences::renders_edits` is the one rule for "this image shows the authored edits"; the color-pick gate compared full settings with `==`, so in Speed mode or with custom tone tuning a pick never started. `RenderOutcome` (rendered, cancelled, failed) replaces `Result<Option<_>>` on replies. Remaining request-id fields are named for ids, and `WorkPlan::wanted` replaces `visible`. Next: move the worker tests to `plan` and delete the test-only `Worker::submit`.

Then, agreed with the owner (vocabulary in the spec):

1. **Names.** Rename to the spec's vocabulary: browser selection, viewport selection, history photos, loading, `ViewMode` (was `View`), visible region, patch region, loupe visible and patch regions. "Displayed", "shown", "tiles" and "held" go.
2. **Lens and visible region before planning.** Derive them from the pointer and viewport state instead of from drawing, so a photo never waits for a lens or screen bounds. Loading is then the only waiting state.
3. **Settings for every viewport photo (revised with the owner).** The editing selection stays a subset of the viewport photos, chosen by clicking tiles. Settings load for every viewport photo, which is cheap, so "loaded settings" stops being a separate bound and a drawn photo never waits on eviction.
4. **No active photo.** The crop and rotation plane, inspection outputs and comparison apply to every viewport photo, including those outside the editing selection; crop, rotation and color picks act on the photo pointed at. Scopes, navigator and information bar show for a single photo. Inspection renders at native Quality for each photo, so check memory and latency with several photos.
   Decisions for step 4 (owner):
   - **Crop and rotation:** every viewport photo shows its crop plane and a drag edits the photo pointed at, without adding it to the editing selection. Crop presets move to a bar under each photo with its own dropdown, so they apply per photo.
   - **Color picks:** a click sets the clicked photo only; a Shift-click samples the clicked photo and sets the whole editing selection, consistent with zoom, pan and double-click.
   - **Single-photo panels:** scopes, navigator and information bar show when the editing selection is one photo. Mini maps and small scopes under each photo are a later exploration.
   - **Progress:** one pass covers a whole multi-photo update, with checkpoint lines marking each photo's image completing within the pass. The bar is a view, not a state machine: the runtime publishes the latest plan's tracked images with their lifecycle from the coordinator (current, waiting, running, done, failed), the worker reports each running request's stage fraction, and the snapshot combines them. Photos that leave the update drop out with the next plan.
   - **Inspection in a full grid:** a slower output switch is accepted; the owner will check it in the app.
   - **Action scope:** pointer actions act on the photo pointed at, Shift extends them to the editing selection, shared controls act on the editing selection and view switches on every viewport photo (spec, "Action scope"). With the Pointer tool, Shift-click keeps selecting a range. One scope function and one edit path implement it, which is also how 4d removes the active photo.

5. **Planning split and GPU-free tests.** `viewport_photo_inputs()` reads each photo's inputs; a pure `plan_photos` returns the publication. Tests per case: loading, failed, Before while zoomed, loupe on an unedited photo, history photos.

## Photo geometry and scale (owner agreed)

Latency trials disagreed on first-image scales: a photo planned before any image showed its size took a half-size default, and the planner rightly keeps a finer image, so the guess stuck (up to 16× the pixels on large files). Old-format previews also reported their own size as the photo's, so sd9/sd10 tiles asked for full size. Density came from whatever was painted. The capture properties' recorded size, with the header orientation, equals `native_extent` for all 28 example photos across Classic, Merrill and Quattro.

- **Geometry.** Capture properties record the orientation (`X3F_ROTATION`). `MetadataSummary::extent` gives the photo's shown size before authored edits, and `MetadataSummary::family` its camera family.
- **Source of geometry.** One owner holds every photo's capture properties: the browser's metadata loader, in its records. It reads every listed photo's in the background and, in a second lane, the photos the plan and the selected photo need without yielding to rendering (a selection holds viewport demand until planned, so a yielding read would never finish). The selected photo's info panel, controls and inspector read the same records; the separate selected-photo loader (`capture.rs`) is gone. The scale owner computes geometry from those properties, so a photo is planned once its settings and its capture properties are read. Recipe resolution stays about edits (coherence review: carrying geometry with it had forced in-memory edits through a disk read). `view_busy` uses the plan's own list of loading photos.
- **One scale owner** (`rendering/quality.rs`). A photo's scale comes from its tile size at the last paint, its zoom, pixels per point, the policy and its geometry with the photo's crop and rotation (uncropped while framing). The Classic smallest-grid mapping lives there. A photo with no recorded size renders at full size (owner). A photo never given a tile, such as an overflowed editing photo, uses the camera's thumbnail scale.
- **Removed.** Both density maps and their reset, `observe_photo_view_density` and the half-size default. A fitted photo's density no longer reads the drawn image; an explicit zoom still does, because zoom is relative to what is drawn. Tile layout uses the recorded size, with a named 3:2 placeholder only while capture properties are read.
- **Edges.** A photo the layout has no room for keeps its last tile, as hidden photos keep their last geometry. A decode-cache entry written before orientations were recorded takes it from its cached decode, so offline cached photos keep their scale. The browser's Width and Height sorting uses the recorded size too, not the preview's.
- **Consumers.** Scale deciders move to the owner: view requests, the zoomed-placement check, frame acceptance, preparation, worker reuse and the smoke harness. Images that exist keep mapping with their own size: display windows, loupe, framing, crop and rotate tools, browser thumbnails and drawn previews.

## Photo facts and processing profile (owner direction)

Other raw formats (likely Fuji RAF in 0.10.0) will decide their processing family from different fields, closer to an image-processor generation than a camera line. Build toward that now without generalizing: X3F stays the only format and `ProcessingFamily` stays as it is.

- **Two places, one per lifecycle stage.** (1) Reading a file without decoding sensor data or calibration gives its `foveonic::source::MetadataSummary`: normalized fields (processing family, oriented size) and the raw properties kept for display. For X3F that read covers the header, section directory, PROP, the embedded preview's EXIF and the saved adjustments. Browsing and planning need these for every listed photo. (2) The family's profile, with full metadata and settings, decides everything family-specific: the graph, source defaults, control capabilities, thumbnail scale, inspection outputs and preview handling.
- **Now (release gate).** Core interprets capture properties once, into a `MetadataSummary`, where they are read. Full decoding and the cheap read complete their properties with one function, and `Metadata::processing_family` shares the summary's family rule; `Metadata` adds what decoding and processing need (sensor layout, processing version, CAMF). The browser record is the GUI's single source of a photo's facts. Controls, inspector, inspection outputs, the information panel and scale read the typed facts, without interpreting X3F property keys (`CAMMODEL`, `X3F_ROTATION`) and without fallback chains through rendered or full metadata. Recipe resolution may read the same core facts itself; it takes the family as decided rather than checking it again.
- **Slice (implemented).** (1) Full decoding and the cheap read complete their properties with one function (`x3f::complete_properties`); they had diverged once already, when geometry had to be added to both. An original-file test checks that both give identical properties for every example photo. (2) The public entry points return the summary: `DecodeCache::metadata_summary` and `source::read_metadata_summary`, through the one constructor `MetadataSummary::from_properties`. `Metadata::processing_family` shares its family rule. (3) The browser record holds the summary and `Browser::metadata_summary` is the GUI's one accessor; `PhotoGeometry` and `oriented_extent` are gone. Scale, comparison layout, controls, normalization, the inspector, inspection outputs and the information panel read it, without fallback chains. Controls take the family as decided: one `controls::normalize(settings, family)` serves the selected photo (from its summary) and render replies (from their metadata). (4) Recipe defaults take the summary and use its family; batch import and noise calibration read its properties. `App::metadata` stays for CAMF presets, export enablement and the Merrill rotation fallback. Core's inspection outputs take the family as decided and use full metadata only for Quattro output details. Accepted edge: a photo whose summary cannot be read (an offline original with an old cache entry lacking header properties) gets the generic panel until its summary is read, rather than falling back to full metadata.
- **Recorded for the second format.** `Metadata` contains the summary (`metadata.summary`) when it is reshaped for the second format, and orientation then exists once; until then `Metadata.rotation` and the `X3F_ROTATION` property both come from the one builder (owner: containment's churn now is not worth it). These still interpret X3F keys and become summary fields then: browser sort and search fields (`query.rs`), the in-camera rotation default (`controls.rs`, `ROTATION`), the camera field in export and batch logs, and the Quattro editing check, which core keys off the model string (`ControlCapabilities::editing_available`). The information panel's formatter displays raw properties and stays.
- **Later (with a second format).** Move the family matches spread through core (`render/recipes`, `settings.rs`, `options.rs`, `inspection.rs`, decode-cache previews, selection and worker) into the profile. Until then, add no new family or property-key interpretation outside these two places.

A newly drawn tile with a non-final output selected renders its final output first and then the inspection output. Source or prefetch metadata could avoid the second render.

- **Split render settings (core, with or before slice 10).** `foveonic::render::Settings` mixes four kinds of values, which is why matching, sidecars and requests keep re-sorting it. Agreed shape: *edits* (the saved recipe), *render parameters* (scale, quality, region, range preview, estimate request), *output options* (size, TIFF color space, processing sections) and *workspace settings* passed with every render. Workspace settings are dynamic, shared across photos and not saved in recipes; adaptive tone tuning is the only one today, and the noise calibration profile is the likely second member. Model them as one group rather than a lone tuning field. Before it, as its own step: the core `Artifact` becomes `Render`.

- Measure whether running several native patches side by side helps on one GPU (`warm_group_latency_by_width`), before changing admission headroom.

## Discoveries

- **Review before commit.** Per-image request ids had broken the layer rule: a stale whole image issued after its patch hid the sharper stale patch during slider edits. Stale layers are now ordered by edits (a patch and whole with the same edits came from one plan), and by id only when edits differ. The progress bar follows one tracked image, the selected photo's first, instead of the last image begun. Only a new whole image cancels a pending color pick; scopes are re-requested on every delivery. `resolve_settings` copies the request's quality once, and `Preferences::with_workspace_settings` (was `render_settings`) applies only workspace settings. A source origin binds only to the exact request that produced the image, so a late image from a replaced file cannot bind its origin to newer work. A waiting photo keeps a view built from its current request, so the loupe can place its lens. Earlier id renames had silently not applied because macOS `sed` lacks `\b`; they are now done.
- **GPU correctness suite not run since slice 9 (worker-test migration).** The view-planning steps relied on unit tests and the two native scenarios. Running the GUI GPU correctness group again found two failures that pass at the last commit. A replaced file's first image was rejected as "source changed" because a new task inherited the previous task's origin when its request knew none; since the migration the delivered-pixel seed is refreshed only for admitted images, so the old file's pixels kept seeding later work. A task now takes only its request's origin (GPU-free test in `coordinator_test.rs`). The comparison test modelled leaving an output as keeping it wanted; it now shows one output at a time like the app. Worker tests now publish through `plan` (`TestWorker` keeps the wanted images), and the test-only single-request command is gone. The test inventory still requires nine GPU tests that no longer exist and needs updating before release checks. `browser::loader::tests::stopping_with_full_image_replies_releases_priority_before_background_join` failed once and passed on three reruns.

- **Scenario captures raced speculative work (review fixes).** "Busy" excludes speculative full-size work, so a step can settle while a full-size image is still coming. The scenario captured images at the end, after saving the trace, and a full-size image arriving in between made the capture differ from the image recorded when the last step settled. Images are now snapshotted in the frame the last step settles and written after the save. Whether it showed depended on how long the trace save took.
- **Before is a shortcut over the current output (review fixes).** Keeping only what a photo shows dropped an inspection image while Before was on, so turning Before off rendered it again. A viewport photo also keeps what it shows with Before off.
- **Viewport photos come from the viewport (migration).** `displayed_photos` first used the editing owner's render paths, which hold only photos the owner keeps. When the editing limit evicted a photo that was still on screen, it left the plan, its image was released and the loupe had nothing to land on. Viewport photos are now the edited photos, the photos the viewport draws for the browser selection, and the loupe photo. A shown photo without held settings keeps its images and renders nothing until the loupe admits it. Found by the transition journey; a GPU-free planning test should cover it.
- **Planner shape (step 1).** The app keeps one whole image per photo and a newer one replaces an older one, so the planner needs only the whole image and the patch, not separate reduced and full-size images. Drawing has no request to plan with, so it calls the planner's `patch_on_top` rule directly instead of reading layers from the plan.
- **Step 2 scope.** Before still uses the coordinator's refinement sequencing when zoomed, so that code stays until Before moves to the planner.
- **Cache-workflow scenario (step 2).** An action now completes when every patch and the whole image behind it have the current edits (`behind-current`). Full-size settlement is recorded when present but no longer required, because with six photos it may never run. Release comparison reads `behind-observed`, which builds before this change do not emit.
- **Step 2 review.** Fixed: a finished full-size image removed the stored patch, so the planner rendered the patch again; a current full-size image now covers the view. The coordinator keeps a replaced request's place in the queue, so after the first edit whole images ran before patches; whole images are now requested only once no photo needs a patch. Full size ignored the background-completion preference. The runtime's unchanged-plan cache was not reset when the coordinator cleared or retired work. A whole image had the higher revision, so a patch with the same edits could be rejected or hidden; the patch is now one revision newer.
- **Open from the step 2 review.** An in-flight patch for a region the view has left is not withdrawn when the plan no longer needs a patch (step 3). Active-photo-first among patches is not guaranteed, because a replaced request keeps its queue place. `Refinement::preview` and the coordinator's preview handling are unused by Current and go with `Refinement` when Before moves to the planner.
- **Six-photo scenario (step 2).** On the performance Mac at a 6 GB target, after each exposure edit all six patches were current within 150–167 ms and every image behind a patch within 317–334 ms. The initial zoom took 1.9 s. No full-size image finished during an action. Before this step the scenario failed because it waited for full size.
- **Step 3.** Settling uses only the 120 ms rest; release is not needed because people release later. Cancelling already worked under the planner: a new region makes a new task, which the worker stops at its next step. The old sequencing had held the new region as pending instead. The review found that withdrawing a patch the plan no longer needs also withdrew finished patches, which made zoomed photos invisible to the working set and evictable; only patches still in flight are withdrawn now. Photos waiting to be redrawn after selection no longer withdraw their in-flight patch. The drag scenario now fails if a patch is requested while the view moves, and checks latency only when a patch, not a full-size image, covers the final view.
- **Six-photo drag (step 3).** The scenario turns full-size completion off from the last exposure edit, because a finished full-size image covers every region and the first run passed without any patch. With that, no patch was requested during a 20-frame drag, and the patch for the final position landed 198 ms after the last move (120 ms settle plus about 80 ms of rendering). No patch for a dragged-past region arrived after the view settled.
- **Open from the step 3 review.** A wheel or pinch zoom that crosses into native resolution starts settled, so its first native frame requests a patch for an intermediate zoom that is then replaced. Cancellation limits the cost.
- **Loupe (step 4).** The loupe supplies its lens region to the planner and settles like a zoomed view, so its separate request, coverage bookkeeping and `loupe.coverage` trace event are gone. Drawing uses the same patch rule. Leaving the loupe retires its patch through the planner, which also now emits one `view.plan` trace event per changed plan, as the spec requires.
- **Images in use (step 5).** The planner returns every image a view uses, ready or not, with the request that made a ready image. The coordinator renders the missing ones and keeps only work matching an image in use for the planned photos (`desire_planned`, `keep_in_use`); its own replacement rules no longer apply to them. Fit view goes through the planner too, so the old overview path now only serves photos the planner does not plan yet (Before renditions and the excluded active photo). A photo that leaves the view is reconciled against no images, so its work stops; a photo waiting to be drawn is left alone. The runtime keeps only an unchanged-publication check, which `clear` resets. `view_busy` (work outstanding or a view still settling) replaces the worker's busy flag for progress and native scenarios.
- **Step 5 scenario findings** (historical; the migration replaced `mark_stale` and `restore_photograph`). The transition journey found three integration gaps, each a case the planner's inputs did not express. Clearing the worker, not `invalidate()`, is what made the old path re-render viewport photos, so clearing now marks their images stale (`mark_stale`); `invalidate()` only republishes. Returning from inspection relies on restoring the kept photograph, which the planner path now calls. A viewport photo the planner does not handle yet (Before, the excluded active photo, a failed render) was treated as having left the view and lost finished work; only photos no longer displayed are now reconciled against no images.
- **Browser cursor and scenarios.** After the browser kept its own keyboard cursor (b7f8a2d), the transition journey stalled at the loupe step: two scenario steps chose an arrow direction from the app's selected photo, so the arrow hit the end of the list. `Browser::arrow_origin` is now the one rule for where arrows start, used by the browser and both steps. The cursor commit had not run the native scenarios before it was committed.

- **Merrill Auto sharpening follows the original (owner).** Implemented: color Auto uses the noise-table base, monochrome Auto 1.25, and the applied amount takes the MED/LOW factors and the square root of the working-size ratio (`applied_sharpen_amount`), so power-of-2 reduced renders sharpen less. Evidence: SPP 6 applies final sharpening to Merrill color photos by default: amount = base + control (control ≥ 0) or base·(1 + control/2) (control < 0), × sqrt of the reduced-size ratio, × 0.8409 for a MED and 0.7071 for a LOW resolution. The base is the camera noise table's ISO-interpolated sharpening value times the selected noise step's, which is 1.0 on every Merrill file checked (DP1, DP2, DP3, SD1). It runs on linear RGB after reconstruction, before tone, using the signed luminance detail. The specs' "Merrill color Auto resolves to zero" came from 3775c84 without recorded evidence; `noise::couplings(..).sharpen_base` already computes the SPP base, and only the Merrill-color branch of `default_sharpen_amount` overrides it. Monochrome photos use a fixed base of 1.25 rather than the table value.

- **Step 2B piece 1: one sidecar path (implemented).** The selected photo no longer has its own sidecar load and `ready`, `writable`, `dirty` and `last_queued` flags. A malformed or newer-version recipe opens with source defaults and a warning, and its next edit replaces it (owner: acceptable before 1.0). `sidecar::load` returns `Saved::{Missing, Recipe, Malformed}`, so export, the decode cache and previews follow the same rule. A recipe file that cannot be read is an error: the photo opens with defaults and `sidecar::save` refuses to replace it while it stays unreadable; once it reads again the next save replaces it (owner accepted). - **Findings while fixing native acceptance (with piece 1).** (1) Import review's edits live only in memory and end when another folder opens. (3) Rendering order is an order, not a gate (owner): the planner no longer holds whole images back while any patch is needed. It publishes everything in priority order, the coordinator lists work in that order, and the executor ranks queued jobs by it (`Job::rank`) and passes over a job still reading its original. Source loading no longer holds back another photo's edit. An A/B against the gated order showed no regression: six photos zoomed to 200% showed first native detail in 333 ms against 350 ms and all six in 2033 ms against 2083 ms, and the latency domain stayed within about 3%.
